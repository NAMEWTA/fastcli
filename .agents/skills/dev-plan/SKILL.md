# 生成票据与实施计划

先保存各切片的 Markdown 票据和同名验收报告，再从票据声明的依赖组装 `plan.md`。用户明确选用本技能时，一个切片也保存一张票、一份同名报告和单节点计划。已经明确且只要求实施的单项由 `dev-build` 直接处理。

每个切片说明目标行为、真实依赖与验收方式；可以采用 TDD 短循环、实现后行为验证或适合该切片的其他方式。

## 先读取当前分支的完整方法

| 当前任务 | 开始前读取 | 产物 |
| --- | --- | --- |
| 目标、行为或验收还有影响出票的缺口 | [决策地图](references/uncertainty-map.md)或对应澄清方法 | 在已有权威记录解决前提，再回到本任务出票 |
| 已有明确需求，需要拆票或制定计划 | [完整出票方法](references/vertical-slicing.md)与[票据与计划模板](references/plan-template.md) | 已保存的本地票据和实施 DAG |
| 已有票据，需要跨阶段或多 PR 安排 | [多阶段计划](references/multiphase-plan.md) | 从同一组票据组织各批交付和联验 |

按当前缺口读取方法，复用已有决定、规格和票据。明确的单项规划使用[最小计划](references/plan-template.md#最小计划)。只读审阅使用[计划核对](references/plan-review.md)，指出缺失票据与依赖，原处修订按本次授权执行。

## 从完整上下文开始

读取本次权威行为契约、相关讨论和已有计划。契约可以在 brief、spec、事项或既有设计章节中，不要求为了规划另建 `spec.md`。用户提供 issue / PR 时读取正文、评论和当前改动。用领域词汇描述任务，遵守本次已经确认的约束与授权。

计划涉及并行、重任务或工作树时，在共享上下文引用已有的 `.agents/dev/context/environment.md` 或等价环境记录；未核实的条件留待实际派发前按执行主机确认，规划不虚构已采集的容量。资源不足决定排队次序，不是票据之间的产物依赖。

定位当前代码和可复用实现。确有结构阻碍时先安排小范围前置调整；不要把泛化重构、工具换代或技术债清理偷偷加入本次范围。

涉及新的布局、交互或用户明确要求的可视化对齐时，先读取 `dev-prototype` 产物及其确认记录。需要影响范围、行为或验收的体验决定时，先完成该决定再出票。行为已明确但仍须取得版本确认才能实施时，在对应票中写明这个前提；已有同内容、同范围确认直接沿用。

影响本次交付范围、行为或验收的未知先查事实，必要时调用 `dev-grill`、`dev-spec`、调查或探索方法。前提明确后接续出票。仍缺必要输入时交回具体待决项与接续点，实施计划保持待完成。

## 切成可交付的行为

每个切片应当：

- 贯穿所需的数据、业务、接口、UI 与验证层，而非“先做数据库，再做全部 API，最后做全部 UI”。
- 完成后可独立演示或给出行为证据。
- 尺度适合一个实施者在可控上下文内完成；超出时按用户行为继续拆分。
- 有独立验收条件与清楚的边界，不依赖实施者猜测“做到什么算完”。

先做能尽早暴露关键假设的最小完整路径，再扩展场景。探索原型交付决定与证据，确认原型交付可操作的体验基线和真实确认记录；两者都不伪装成已完成的产品功能。

为每个切片记录**真实阻塞**：只有前项的产物、决定或共享不变量确实是开工前提时才连接依赖。无阻塞切片可以同时推进；“看起来顺序更整齐”不是依赖。

## 对复杂重构使用诚实的整合边界

跨全仓库的机械改动可能无法按功能切片单独保持可运行。此时明确一条整合分支及最终统一验证边界。

若项目确实要求迁移期间持续兼容，可采用“扩展 → 分批迁移调用者 → 删除旧接口”；只有这种约束存在时才保留过渡层。用户已经允许直接替换时，规划一次完成全部调用者迁移及旧实现清理，不凭空引入兼容包袱。

说明哪些中间提交允许暂时不可运行，以及哪个整合点必须完整通过验证。中间状态不能被标记为可部署交付。

尚不明确的大需求按决策地图区分“已能表达、答案待查”和“还无法定义”的问题。调查和产品决定写在现有记录，解决出票所需前提后形成实施票。

调用 `dev-grill` 时传入具体未决选择、已确认决定、它的依赖及权威记录位置。已有问题文件就把答案写回该文件，地图只追加要点与链接；没有问题文件时沿用现有需求或决策记录。访谈完成后回到当前规划，不另建一份 brief 或重新启动完整需求流程。

## 写票据，再组装计划

使用[票据与计划模板](references/plan-template.md)，在同一 Change 内保存：

- 每票一个 `tasks/<NN>-<slug>.md`，同时建 `evidences/` 内完全同名的一份 `.md` 并链接它，未执行就标「未验证」。按[本地工作记录](references/local-work-records.md)检查两个目录一一对应。任务正文及直接阻塞边由原票维护。
- 通读已保存的本地票据，再组装 `plan.md`。计划给出整体目标、共享契约与环境、依赖 DAG、当前可开工项、接续点、整合负责人及最终验收。
- 实际进展写回票据或既有 `progress.md`，计划链接所选的权威进度记录。按[本地工作记录](references/local-work-records.md)处理旧计划、只读宿主和外部链接。

任务正文写交付行为和验收，不写逐行修改教程。交给新会话或独立实施者时，使用[单个切片](references/plan-template.md#单个切片)补足来源与必要背景、本项规格范围、已定约束、前置产物和验证入口；已有任务原处补足，不另建一份正文。资料指针必须能被接手者实际读取，不能共享时提供必要原文。

代码导航与行为契约分开，区分已有入口与拟新增文件，实施时复核；跨阶段安排才使用完整多阶段模板。验收写条件、动作与可观察结果，按真实风险覆盖正常、失败和回归；每项都能找到验证动作与通过判据，不用“测试通过”代替行为判断。信息密度可参考[任务示例与反例](references/task-examples.md)。

对适合并行的工作明确唯一写入者与文件/模块边界，同时核对共享 API、数据模型、迁移序列和测试资源；不同文件不等于互不冲突。先稳定共享契约，再推进独立消费者；不让多个代理同时覆盖同一分支或同一共享文件。

## 交付前核对

按[计划核对](references/plan-review.md)检查粒度、阻塞、交付与验收，并从规格反查是否有遗漏、重复责任或未承接的消费者。多切片按需使用[规格覆盖表](references/plan-template.md#规格覆盖)，保留用户明确的数量与交付边界，不把票数当成交付数量。

前置产物可用后，本项应能完成自己的验收；跨任务的整合验收另有明确归属，不把未来工作藏进早期任务的完成条件。全部任务勾完仍需核对原始目标和整合结果，规划中的预期证据不代表已经通过。

## 进入执行

如果用户要求先审方案，交付计划后停在所要求的位置。如果已经要求持续实施，说明计划并按授权继续；只为影响目标、不可逆操作或确实缺失的产品决定寻求补充。

需要发布到 GitHub 时，由 `dev-issue` 将当前票据和计划组织为可认领正文，并提供接手者可访问的版本链接。Issue 收录必要背景、交付与验收，注明本地权威来源；任务正文、阻塞边与实施进展仍在原票据或已有进度记录中维护。远端讨论产生的新决定按[本地工作记录](references/local-work-records.md#外部事项)同步，创建、关联或关闭外部事项分别按现有授权执行。

实施时工作前沿是“所有阻塞已满足的切片”。完成一项就更新依赖事实，继续推进可开始的下一项。不用预设状态枚举或复杂 Schema。

实施授权已明确时调用 `dev-build`，交回权威规格、`plan.md`、接手的票据路径、适用的确认原型版本与范围、前置产物、写入边界、验收及当前证据和授权终点。缺少相关体验确认时交 `dev-prototype`，继续不依赖它的已授权工作。保存交接、接续与明确暂停由 `dev-handoff` 负责，持续协调由 `dev-workflow` 负责，交付操作由 `dev-deploy` 负责，沿用同一记录。

## 按需补充

| 当前缺口 | 方法 |
| --- | --- |
| 组织实现分工与共享写入边界 | `dev-build`（功能执行） |
| 还缺产品选择或准确术语 | `dev-grill`（决策访谈）、`dev-architecture`（领域建模）、`dev-archive`（词汇表格式） |
| 需要记录持久取舍 | `dev-archive`（决定记录格式） |
| 未知问题能通过实际运行解决 | `dev-prototype`（探索方法、逻辑探索或界面变体） |
| 未知问题依赖技术资料或代码事实 | [研究方法](references/research-method.md) |

本包资源使用链接，其他方法按技能名调用。复杂模板提供完整可选覆盖面，不要求小任务机械填满全部栏目。

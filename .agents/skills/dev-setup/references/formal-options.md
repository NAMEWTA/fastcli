# 配置形式化验证接入

先核对工具、配置和已有入口。建立属性、选择验证方法、建模、解释反例与防止模型漂移由 `dev-formal-verify` 负责；先查项目是否已有模型、证明、验证器或项目技能，能复用就不另建体系。

## 记录已有范围

读取任务已经声明的性质及范围，例如重试不会导致同一副作用重复提交、一个作业不会同时运行两次、解析器拒绝某类非法结构。引用现有模型与代码映射、输入和状态边界、并发假设及外部依赖。尚未选定高价值属性时，由 `dev-formal-verify` 判断需要分析什么；单纯配置宿主不自动增加形式化工作。

## 核对工具接入

优先项目已有可运行工具。记录真实可执行文件、版本、配置位置、命令、资源限制与结果路径。不同模型格式使用兼容入口：JavaScript 有限状态模型使用其 Node 检查器；TLA+ 使用实际可用的 Java/TLC，只有选择 TLC 结果展示时才调用 `dev-statechart`。环境检查不能代替模型与代码映射的审查。

需要创建或维护检查时，将范围、已有模型、真实工具与授权交给 `dev-formal-verify`，取得其执行入口和限制后继续配置。缺少必需技能或验证器时说明具体缺口，继续不依赖它的配置；不把临时编写另一套方法或安装无关工具当作配置步骤。

## 接通现有检查入口

用户范围包含运行既有检查时，使用已确认的模型、配置和真实验证器，工具原件按需留项目根 `temp/dev/`，命令、版本、退出结果和产物位置更新到实际 task 的同名报告。已有同版本、同配置的有效证据可以引用；达到时间或状态上限而未穷尽属于未完成。只有入口已配置而未运行时，明确标为尚未验证。

实际反例、检查辨别力和模型漂移交回 `dev-formal-verify` 处理，沿用同一证据与记录。配置任务不能删掉属性、削弱边界或把失败改写为成功。

## 保存配置并返回

在现有环境记录中保存工具、配置、调用命令和验证入口的指针，不复制模型、假设或完整证明记录。需要项目专用技能时由 `dev-formal-verify` 在指定源仓库生成，新建形式验证包使用 `dev-formal-verify-<area>`，安装到 `.agents/skills/`；已有包沿真实位置维护。

工具、接口或模型条件变化时，交接具体变化与原证据，按影响重新核对配置或模型。交付区分已配置、已运行、受阻和未覆盖；配置选择不是属性已经被证明。

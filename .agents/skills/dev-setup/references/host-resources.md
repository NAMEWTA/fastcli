# 主机资源与任务准入

本方法负责环境核验、容量估算和准入记录。使用现有宿主、系统观测命令和调度能力；工作树创建、父分支集成与清理由 `dev-worktree` 负责。资料读取不扩大为软件安装、远端部署或全局配置修改。

## 执行范围与环境要求

1. 确认实际执行位置、仓库与目标检出、时间和时区，以及当前是在物理机、虚拟机、容器、WSL 还是远程工具中。工具在服务端运行时，不把执行器资源称为用户电脑资源。
2. 本机默认检查；远端只按用户给定的主机、连接或项目既有明确目标，通过现有 SSH、MCP 或管理接口做只读核验。不扫描网段、枚举未指定主机或读取凭据明文。不可达目标标为未核实且不可派发，不推断其空闲容量。
3. 从项目清单、锁文件、版本约定、容器定义、CI 与现有启动/验证说明提取所需运行时、包管理器、编译器、浏览器和必要服务。先读入口再运行；比较要求与实际版本，不以“命令存在”代替兼容性。
4. 在真正执行任务的主机和 worktree 核对依赖、工作目录、端口与可访问服务。主检出能运行不证明新 worktree 已初始化；环境不匹配时记录受阻动作和可继续的只读工作。
5. 为物理主机、可见父配额和共享存储标记资源池关系。两台主机共享 NAS 时磁盘是同一池；同一主机上的多个容器同时受各自及公共上限约束。未知拓扑不得当作独立容量相加。

## 读取有效资源

优先复用已有监控和宿主只读接口。只记录任务需要的摘要与采集方法，不保存完整进程命令行、环境变量或秘密。下列为按系统选择的观测入口，不是要求每台机器执行全部命令。

| 位置 | 观测入口 | 判读重点 |
| --- | --- | --- |
| Linux | `uname -srm`、`nproc`、`free -b`、`vmstat 1 3`；按需读 `/proc/meminfo`、`/proc/pressure/` | 用可用内存及短时压力判断，不用单独的 free 字段；swap 不是可任意追加的 RAM |
| Linux 容器/服务 | 结合 `/proc/self/cgroup`、`/proc/self/mountinfo` 定位实际 cgroup，读取当前层及可见父层的 `memory.current`、`memory.max`、`memory.high`、`cpu.max`、`cpuset.cpus.effective`、`pids.current`、`pids.max` | 取适用约束中最紧者；`max` 不是 0；`memory.high` 是回收/节流阈值，区别于硬限额。cgroup v1 使用其实际对应接口 |
| macOS | `sysctl -n hw.logicalcpu hw.memsize`、`vm_stat`、`memory_pressure -Q`、`sysctl vm.swapusage` | 结合页大小、压缩与压力估算；不能把总内存或 free pages 直接等同于可分配量 |
| Windows | `Get-CimInstance Win32_OperatingSystem`、`Get-CimInstance Win32_ComputerSystem`、`Get-Volume`、`Get-Process` 的必要字段 | `FreePhysicalMemory` 以 KiB 计，磁盘与工作集常以字节计；容器、Job Object、WSL 限额另行核对 |
| 文件系统 | 对仓库、worktree、依赖缓存、构建输出和临时目录分别用 `df -Pk <实际路径>`；适用时用 `df -Pi <实际路径>` | 未建立的路径查其最近存在的父目录；按真实卷、可用配额和 inode 去重，不能重复相加同一卷的余量 |
| 活动进程 | Unix 可用 `ps -eo pid,ppid,lstart,rss,comm`；Windows 按需读取进程 ID、启动时间、工作集及宿主实例 ID | 关注完整任务进程树与现有服务，RSS 可能重复计共享页；没有权限的字段标未知 |
| Git 检出 | `git worktree list --porcelain -z`；需要详情时调用 `dev-worktree` 只读审计 | 纳入主检出、活动、闲置、集成树与原生宿主管理的实际路径，不把分支数当工作树数 |

计算前统一单位：内存、磁盘和对应任务需求统一为字节；`df -Pk`、Unix `ps` 的 RSS 和 Windows `FreePhysicalMemory` 按 KiB 转换，页数乘实际页大小。CPU 用有效核数，inode 用数量；cgroup 的 `pids.current/max` 按包含线程的 TID 数量计数，不能用进程列表行数代替。保留原始单位与换算方法，表格可再展示为 GiB。

CPU 容量使用亲和性、cpuset、适用配额共同限定的有效值；`cpu.max` 的 quota/period 可以是小数核。短时空闲和负载只用于校验压力，不把当前低利用率当作未来可预留核数。内存新增余量不超过可用 RAM 与各适用 cgroup 剩余额度的最小值。看不到宿主或父级限制时记录边界，不能宣称已经核实全机容量。

磁盘计入依赖安装、编译缓存、日志、截图和临时解包峰值。共享包缓存只计算一次固定占用，每个 worktree 仍保留实际增量；硬链接和写时复制不保证后续写入免费。`tmpfs` 同时受内存约束。存在本地模型、GPU 任务时才核对显存等额外资源；调用远端模型不等于本机加载了模型权重。

## 测量工作负载

按实际动作建立少量负载类别，例如只读研究、代码实施、依赖安装、构建、单元测试、浏览器验证、集成。区分 Agent 会话常驻成本与附加重任务成本；同一进程不能在两类中重复计数。

- 复用当前主机、工具版本、项目规模和 worker 设置仍适用的峰值样本，注明测量范围。项目升级、测试规模或嵌套 worker 改变时重新校准。
- 新类别没有可靠样本时，先标未校准；余量足够且风险可控才运行一项有界的代表任务。记录完整进程树峰值、CPU/进程需求、最大磁盘增长和结束后残留，不同时放大多项未知负载。
- 原生监控、cgroup 统计或已有测试性能工具优先。观测窗口未覆盖真实峰值时，给估算留不确定性余量；单个父进程的最大 RSS 不能冒充整棵树同时峰值。
- 校准不能用尽机器。系统、桌面、常驻服务和未知背景增长都要保留空间；优先沿用用户/平台既有保留值，否则根据当前测量写出保守假设和理由，不编造“每个 Agent 固定占几 GB”的通用常数。
- 测量启动前记录任务负责人、host/pool、worktree、宿主会话或服务 ID、PID/进程组与启动时间、停止入口。PID 会复用；结束回收时必须重新核实身份。

## 计算可新增容量

预算是当前执行组合的准入上限，不是机器的永久性能承诺。按每个主机和每个共享资源池分别计算，再取该任务涉及的全部限制中最紧者。用户给定值只能进一步限制已验证容量，不能把未知容量变成已知。

内存、磁盘、inode 和 PID 等按当前剩余量计算的资源维度 `r` 使用同一种口径：

```text
H_r = 当前有效剩余量
B_r = max(0, H_r - 额外保护余量_r - 尚未体现在当前占用中的预留_r)
```

`H_r` 使用本次实际剩余量，已运行进程和现存文件已经反映在其中，不能再次扣同一份占用。仍要扣除运行中任务从当前占用增长到已预留峰值的部分，以及已准入但尚未启动的预留。无法分辨已兑现部分时，保守保留整项预留并注明可能低估容量。

CPU 单独按承诺量计算：`B_cpu = max(0, 有效核数 - 系统保留核数 - 运行中与待启动任务的全部已承诺核数)`。这里已经扣除待启动预留，不再套前式二次扣减；不以瞬时空闲率替代承诺量，也不在重算时丢掉运行中任务的 CPU 预留。

负载类别 `k` 的新增数量同时满足每个相关维度的 `n_k × demand[k,r] ≤ B_r`；混合负载使用 `Σ(n_k × demand[k,r]) ≤ B_r`。需求已知且大于零时，单一类别可取各维度 `floor(B_r / demand[k,r])` 的最小值，再受用户、运行时、API 配额等上限约束。明确不消耗的维度可略去；未知需求不能按零除数或无限容量处理。

分别报告下列数值及其假设，不把三个上限当作能同时独立用满的额度：

| 维度 | 必须说明 |
| --- | --- |
| Agent 会话 | 当前活动数、包含 Lead 的总上限、当前可新增数；子代理、多个 CLI 会话与会话间共享服务分别如何计数 |
| 重任务 | 每类重任务及其内部 worker 的上限、当前活动数、可新增数；Agent 可以继续只读工作而等待重任务名额 |
| 保留 worktree | 当前数量和空间、在指定负载/保留条件下的总上限及可新增数；额外安装与集成树预留；闲置树仍占磁盘 |

示例仅解释计算：某资源池采样剩余内存 10 GiB，额外保护 2 GiB，已准入任务尚未体现的峰值增长 2 GiB，则新任务预算为 6 GiB。若实测一个新会话的常驻需求为 1 GiB，它附加的构建需求为 3 GiB，可放入两个会话与一个构建，共 5 GiB；不能同时放两个这样的构建。CPU、磁盘和其他限制还须分别满足。这里的数值不是默认配置。

无法证明一次新启动可容纳时，新增量为 `0`，说明是环境缺失、关键观测未知、等待回收还是容量不足。保留可做的轻量工作或排队；不能用 `max(1, capacity)` 强行放行。远端有余量也只接收能够在那里实际执行且已获准的任务，本地编译不能借用远端空闲 RAM。

## 预留、派发与复测

1. 复用现有调度器的原子预留或单一负责人串行准入。项目记录默认在 `.agents/dev/context/environment.md`；多个检出传递同一权威路径。多个仓库/会话共享池时沿用已有公共协调入口；无法协调时不让每个 Lead 各自占满同一快照，应保守串行并注明未管理的背景负载。
2. 在派发 Agent、创建或初始化 worktree、开始重任务前重新读取相关实时量，与当前预留合并检查。先记录任务/所有者、host/pool、工作量、预留和释放条件，再启动。批次需要额外集成树时，先保留一个可复用集成树的磁盘空间及后续验证容量，再分配叶子任务；不能等所有未合并子树占满磁盘后才申请集成空间。子协调者与嵌套 Agent 从同一预算分配，不获得一份新的整机额度。
3. 明确区分“依赖已经满足”和“资源允许启动”。资源不足只是排队，不改变任务 DAG，不减少必须完成的候选总数或验收范围。失败重试与替换执行者也要经过准入；原进程未确认结束时保留其占用。
4. 将实际可用的宿主并发开关、构建 `jobs`、测试 worker 或浏览器 worker 限制映射到分配额度。先核对当前版本、字段和作用域；单会话子代理上限、API 额度、Node 堆限制、容器隔离都不能代替整机预算。需要硬限制时复用已授权的容器/服务管理能力，不擅自改全局参数。
5. 新一轮派发、任务退出、恢复会话、换主机、依赖变化、首次重任务、清理后或出现 OOM/内存压力、持续 swap、磁盘/inode/PID 紧张时刷新。记录有效条件而非默认把旧快照永久有效。长任务使用已有监控/事件或合理间隔采样，不忙轮询，不声称创建了不存在的守护进程。
6. 出现压力先停止新派发与重试风暴，再降低可控 worker、排队或有序停止本任务可恢复进程。保留用户和其他任务的服务；没有安全停止入口就记录占用和阻塞，不按进程名称批量杀进程。压力解除并重新测量后才恢复名额。

## 回收与交付

收尾或容量不足时，将已完成且已合并到直接父分支的 worktree 候选交给 `dev-worktree`：传入真实主机/路径、完成与合并证据、用户保留要求、会话和进程身份。先核实本任务实例退出，再按已有方法处理工作树与登记。文件、进程、容器或共享缓存的回收范围各自核实，不因一个任务结束就全局删除缓存。

回收失败或仍有后台进程时保留相应预留。成功后重读目录登记、进程状态和实际卷空间，只释放确认结束的部分；`git worktree prune` 不会停止进程，也不能代替现存工作树删除。把未释放项和理由交回原任务，恢复会话时重新核验，不照抄旧空闲量。

按[环境记录模板](../assets/environment.md)保存摘要、来源、计算口径、置信边界、验证与刷新条件。上限来自观测和可审查假设，真正的硬保障取决于实际运行时和操作系统限制，不能宣称 Markdown 本身阻止了所有资源耗尽。

# 并行工作与候选比选

先判断哪些工作可以独立推进、哪些产物需要等待。选用并行时，明确各项工作的输入、可写范围、交付物与整合条件。派发前复用 `.agents/dev/context/environment.md` 或已有权威位置中仍有效的资源信息；缺失或过期时按本机及用户指定执行主机的当前情况核对。统一分配名额，资源不足时分批完成相同范围；关键容量未核实时先补查，不扩大并发。

## 选择形态

| 目标 | 方法 | 结果 |
| --- | --- | --- |
| 已选定集中协调多个执行者，需监督多项交付 | [多执行者项目协调](references/program-coordination.md) | 当前产物、验证结果及待决事项 |
| 已选用分工覆盖不同模块、风险、平台或证据来源 | [分工覆盖](references/parallel-coverage.md) | 每个必要切片都有结果、证据或明确缺口 |
| 同一产物存在多种可行形态 | [候选比选](references/candidate-comparison.md) | 按共同标准选基础方案，吸收其他候选的优点并验证 |
| 部分工作需要覆盖、部分需要竞赛 | 先拆范围，再为相应切片选择方法 | 一份集成报告，保留各部分选择规则 |

任务本身很小、共享写入无法安全隔离、或没有实质方案差异时，直接完成更合适。采用顺序推进时也可按相同范围验证覆盖。只有取得独立判断时才将结果记为独立复核。

## 执行约定

1. 写清完成条件、产物、允许修改范围与验证方式。竞赛先声明首个通过、全部排名还是择优；不要看完结果后再改胜出规则。
2. 指定准确输入版本。比较提交时给出 SHA；性能比较写明工作负载、样本定义、样本数与顺序。旧提交的结果不能代替当前制品。
3. 按`dev-guardrails`（共享写入隔离）分配文件、工作树或输出目录。需要工作树时调用 `dev-worktree`，同一直接父分支的实施结果按批逐项集成。多个执行者不能同时改同一个索引、分支或状态文件。只有确实需要共享写入时才使用实际锁或单写入者机制。
4. 实际分工时，每份[执行简报](assets/worker-brief.md)独立可读，包含必要背景与边界；不让执行者猜父任务。传入执行主机、已核对的资源条件和本项预留，有环境记录时引用同一位置；在实际工具上限与剩余资源共同允许的范围启动，子级从该预算分配。
5. 收齐结果，核实证据、输入版本与方法，再集成。核对本项启动的实例是否退出，只归还确认释放的预留，待合并工作树按 `dev-worktree` 收尾。缺失、退出或未验证不是通过；需要补一次调查时明确缺口，不无限重试。
6. 多方案任务完整读完候选，逐项评分，先选一致的基础设计，再有理由地融合。使用`dev-guardrails`（统一设计整合），不拼贴互不兼容的方案。
7. 对集成后的产物取得`dev-guardrails`（实际行为证据）。多个候选分别通过，不证明融合后的结果正确。

## 项目记录

将本次需求新增的简报、候选索引、评分与结果统一放到 `.agents/dev/changes/<日期-主题>/parallel/`，代码改动仍留在真实工作区或隔离工作树。比较记录保留取舍、未决项和支持判断的指针；原始运行输出、截图和日志留在项目根 `temp/dev/` 的各候选运行目录。验证结论交回原 task 的同名报告，不创建并行版本，不保存无关原始聊天。

需要比较或综合多份结果时，用[结果与综合记录](assets/result.md)留下选中方案、融合项、否决理由、退出情况和验证范围。只把能帮助后续决定的知识提取进项目 notes；临时执行者状态不成为永久知识或复杂状态机。

## 判断质量

优先`dev-guardrails`（较小且一致的改动），关注`dev-guardrails`（读者需要追踪的层级与状态）。按`dev-guardrails`（上下文预算）提供最相关材料，不把全部仓库和历史复制给每位执行者。

读写远端、推送、评论和部署仍受当前用户授权范围约束。并行分工不能扩大授权，也不能把子智能体的自述当成最终验收。

# 探索原型

探索原型是**用来回答一个未决问题的一次性代码**。问题决定形态。文档已收敛、需要用户确认完整 change 效果时，直接使用 [change 确认方法](change-prototype.md)，不把该任务缩减为单问题试验。

## 选择分支

根据用户提示、周围代码，或在用户在线时询问，确定要回答哪个问题：

- **“这个逻辑／状态模型是否合理？”** → [逻辑原型](logic-prototype.md)。构建可分享的单个 HTML 文件，包含自由操作按钮和分标签引导演练，用非开发者也能操控的方式，把状态机推进到纸面难以推演的场景。
- **“它应该长什么样？”** → [界面原型](ui-prototype.md)。在同一路由生成几种截然不同的 UI 变体，通过 URL 查询参数和底部浮动栏切换。

两个分支产出完全不同的成果，选错会浪费整个原型。如果问题确实模糊且无法联系用户，默认选择更符合周围代码的分支：后端模块选逻辑，页面或组件选 UI，并在原型顶部写明这个假设。

## 两个分支共同的规则

1. **从第一天起就把探索代码当作一次性代码，并明确标注。** 把试验代码放在实际会使用它的位置附近，即被验证模块或页面旁，让上下文一目了然；命名要让随意浏览的人也能认出它是探索试验，不是生产代码或已确认的 change 基线。一次性 UI 路由遵守项目已有路由约定，不发明新顶层结构。
2. **启动极其简单。** UI 原型通过项目任务运行器中的一条命令启动，例如 `pnpm <name>` 或 `node <path>`。逻辑演示是用户双击即可打开的单 HTML 文件。无论哪种，启动都不应需要思考。
3. **默认不持久化。** 状态放在内存。持久化是原型可能正在**检验**的对象，不应成为它的依赖。如果问题明确涉及数据库，使用临时数据库或本地文件，名字应明确包含“PROTOTYPE, wipe me”。
4. **探索阶段略过无关打磨。** 不写测试，不做与当前问题无关的错误处理或抽象，但应确保试验**能运行**，正在检验的失败分支必须可观察。目的在于快速学到东西；最终确认原型仍需完整相关状态与实际走查。
5. **展示状态。** 每次动作后，逻辑原型应输出或渲染全部相关状态；UI 原型在每次变体切换时也应如此，让用户看清变化。
6. **结束时留存。** 记录结论和它解决的问题，把探索原型作为**一手资料**保留：沿用项目现有试验位置，或在隔离分支保存，并在需求记录留下本地路径或分支与提交的上下文指针；远端推送遵循现有授权。涉及本 change 最终体验时，先按 [change 确认方法](change-prototype.md)把选定方向补成完整可交互版本并取得实际确认，再由 `dev-build` 按生产约束实现。确认原型及其资源长期保留在 change 或项目认可的设计位置，不受探索分支的临时留存规则限制。

探索只回答问题，不等于最终体验确认或正式交付。正式实现根据已明确并完成必要确认的行为选择测试先行、实现后验证或组合方法；保持数据隔离，不让生产构建暴露试验分支或选择器。

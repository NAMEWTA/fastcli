## 接收当前 change

本方法默认用于已理解并收敛的需求，让用户通过看见和操作，确认最终产品是否符合自己的意图。完整需求是本次约定的范围，不是为填模板临时扩展的功能全集。

1. 找到同一 change 的原始请求、讨论、最终需求、用户故事、规格、设计、现有计划与限制。读完影响产物的完整材料，不凭最后一段摘要生成页面。外部资料继续引用真实位置。
2. 区分已确认决定、仍有歧义的决定、当前实现和明确允许改变的旧行为。已有认可不重问；事实从源码或运行中查，真正的产品歧义交 `dev-grill`。
3. 指出这次需要用户判断的实际效果，例如“创建后仍停留列表，详情在右侧打开”，而非泛泛询问“这个方案可以吗”。以用户角色、对象、入口、动作和结果描述范围。
4. 找到已有原型与确认记录。若完整资源、范围及用户决定未变，直接复用；不因进入新会话重复制作或审批。若只覆盖部分旅程，补齐缺口，不能把局部认可扩展成整个 change 已确认。

没有正式文档的小需求可以使用已明确的对话共识和简短规格，不强制先产出大量 Markdown；影响流程或语义的冲突则不能凭想象定案。

## 读取项目设计事实

读取对应业务所在的真实页面与承载区域。一个组件应放在它实际将出现的导航、页头、侧栏、列表密度与内容上下文中评估，不能在孤立白板上换掉整个项目的组织方式。

按需记录少量直接来源：

| 需要继承的部分 | 优先查什么 |
| --- | --- |
| 信息结构与导航 | 当前路由、页面骨架、栏目、主要操作位置、详情承载方式 |
| 视觉 | 组件库、实际 CSS 变量、语义颜色、文字层级、间距、边框、圆角、图标、字体与主题 |
| 交互 | 表单验证时机、弹层/抽屉、返回与取消、选择与批量操作、状态反馈、键盘与焦点 |
| 适配 | 目标设备、断点、滚动容器、长内容、省略/展开方式、减少动效偏好 |

记录文件与符号，必要时附页面截图和代码版本。优先现有组件与资产，其次项目已有成熟参考，再选择必要依赖；没有证据时明确未知。用户认可的视觉参考与当前代码冲突时，按最新明确意图决定采用范围并记录理由。

技术栈、产品类别或“现代感”不能代替风格证据。已有设计方向不重新做三套候选；若确实需要比较未决方案，使用探索分支并将结论带回本方法。调用 `dev-ui-design` 只补当前缺口，避免重复建立设计系统。

## 把需求变成可操作旅程

在现有记录中为本次每条需求找到去向。需要时使用[记录模板](../assets/prototype-review.md)的覆盖表：

| 项目 | 要说明什么 |
| --- | --- |
| 需求/故事 | 来自哪个已确认要求，涉及哪个用户和对象 |
| 起点与前提 | 从哪里进入、初始数据/权限/选择是什么 |
| 操作与中间状态 | 用户做什么，系统如何等待、校验或转移状态 |
| 可见结果 | 数据、列表、详情、按钮、导航和反馈如何共同改变 |
| 取消/失败/恢复 | 能否返回，失败是否保留输入，何时重试、撤销或重新开始 |
| 原型证据 | 实际页面/场景、HTML 控件、CSS 状态与 JS 行为定位 |
| 后续验证 | 哪部分是模拟，生产中还需验证哪个真实入口/副作用 |

覆盖本 change 的完整旅程，不只首页或成功路径。正常、空、加载、错误、权限不足、禁用、重复提交、取消、返回、重试、删除确认、长内容、主题、响应式和键盘等，按真实需求与风险选择。不存在的状态写不适用及原因；未做的要求写缺口，不能默认通过。

不可见要求例如服务端鉴权、事务、性能预算不能由模拟 UI 证明。将它们映射到规格和生产验证入口；如果它们影响可见体验，仍需演示对应反馈。不能因 HTML 没有后台就删除这些要求。

页面多时先跑通一条完整旅程，再补全部相关旅程与共享状态。可以分批给用户反馈，但最终整体确认必须能打开串联后的完整版本，不能把几个不连通页面的分别认可当成整体闭环。

## 构建可独立体验的 HTML

### 选择最低成本的可靠载体

默认 `.agents/dev/changes/<日期-主题>/prototype/index.html`。已有有效设计位置可沿用，在同一 change 引用固定版本。项目记录不能写进 `.agents/skills/`。

- 简单场景采用自包含 HTML/CSS/JS，直接打开就能使用。
- 复杂场景可复用项目当前框架、组件和构建方式，再输出有完整资源的 HTML 入口。保留必要源码和构建说明；不要为原型更换项目技术栈。
- 使用模块、请求本地 fixture 等导致不能通过 `file://` 打开时，提供项目已有的一条本地预览命令，并实际核对入口。不要声称可双击打开却依赖未运行的开发服务。
- 字体、图标、图片、CSS、JS 与 fixture 应可随原型取得。避免以漂移 CDN、临时会话、缺失文件或真实账号作为基本可体验前提；必须依赖的外部服务应被明确列出，不能只算本地文件指纹就说整个依赖被冻结。

只保留演示所需内容。生产页面里没有的技术解释、测试控制和状态调试不混入业务流程；必要场景/重置控件放在明确区分的演示区。新原型使用目标项目风格，包内采购示例仅用于学习证据定位。

### 让交互真实改变模拟状态

把状态与渲染分开管理，采用适合当前问题的纯函数、reducer 或小型状态模块，不必引入框架或通用状态引擎。按钮调用行为，行为更新数据，页面重新呈现一致的列表、详情、计数、可用动作与结果。

例如创建任务：打开表单 → 错误输入显示校验并保留输入 → 修正并提交 → 展示等待 → 新任务出现在列表 → 打开详情 → 修改后回到列表仍一致。失败时应能看到失败原因、保留必要上下文并重试。仅显示“创建成功”的 toast 不构成这条闭环。

使用虚构且有真实长度/密度的数据。将外部调用替换为确定性模拟成功、失败、等待或权限结果，不发送真实邮件、不操作真实服务器、不收费、不写生产数据、不携带秘密。

提供自由操作和重置。复杂场景补充领域语言的 walkthrough：说明前提、可点击步骤和应观察结果，每次从已知初始状态开始。用户可以任意探索，不被锁在唯一顺序里。需要持久化体验时采用隔离的模拟存储，并说明刷新/重置的语义；默认内存状态即可。

## 检查完整交互

先完成可审查的结果，再提出最终确认。用实际可用的浏览器或项目验证能力：

1. 从交付方式打开最终 HTML，确认资源加载；实际点击导航、表单、选择、详情和每条闭环，不只检查源代码。
2. 依次走覆盖表中的正常与异常/恢复路径，再自由试探错误顺序、取消后再开、重复点击或长内容。检查数据状态和视觉反馈同步。
3. 按目标设备检查同一视口、主题、内容密度、布局、滚动与弹层；检查 Tab、Enter、Escape 等适用操作、焦点返回和表单错误定位。
4. 修正实际发现的问题，重走受影响路径。共享 CSS/JS 变化会影响多个场景，不只检查当前页。
5. 记录实际观察、版本、场景和限制。截图/录屏写到目标项目根 `temp/dev/` 的本轮目录，按页面、状态、视口、主题标注。它们是补充证据，不替代已确认的 HTML、资源和操作结果。属于实施 task 的验收结论更新它的同名报告；实际用户确认仍保存在确认记录。

自动化可以支持重复风险检查，不为可逆文字调整堆叠测试，也不能用 DOM 计数或关键词断言替代行为验证。没有浏览器时可检查结构/引用，但必须标明未做视觉与交互检查并请用户实际体验；不能写“全部通过”。用户的实际走查可以成为证据，但其未提到的场景不自动获验。

## 取得真实用户确认

向用户提供入口、版本、需体验的完整旅程、模拟边界和明确待确认事项。用户应能判断“这是否是我最后要用的效果和操作方式”，不只评价页面是否好看。

记录实际反馈所在的会话/评论/文档、时间、原话或忠实摘要、对应版本及认可范围。只有实际收到的明确反馈才能填写确认结论；空白模板和模型生成的“用户已确认”没有效力。

用已有 Markdown 走查记录与 Git/快照承载这些事实，不另建 `prototype-version.json` 一类流程/确认状态清单，不让多个文件各自维护“已批准/待批准”。内容指纹按需写入现有记录；业务模拟的 JSON 数据仍可正常使用。

以下情况不能冒充确认：

- 自动测试通过或 Agent 自己完成演示。
- Agent 点击页面上的“确认”控件；页面按钮不是可信用户身份凭据。
- 用户此前认可文字需求、允许开发/创建 PR/合并，或默认未反对。
- 用户只说某个颜色不错，却被扩展为认可全部状态与流程。
- 截图被认可，但未展示的完整交互被推断为已认可。

自然语言明确同意可以构成确认，不强制签字系统、指定句式或重复点击。已有同内容同范围的认可直接引用。反馈要求改变布局/行为时，先做出可体验修订、检查并说明差异，再让用户确认受影响部分；不要求重审无关内容。

需要但尚未获得确认时，清楚标注“待用户确认”或实际剩余范围，不把原型降级成已完成产品，也不启动依赖该体验选择的实施。其他已授权且不依赖此决定的工作继续。此处等待源于用户要求最终效果确认，不能被一般自主执行规则代替。

## 保留版本与处理变化

版本必须覆盖完整 HTML 及其资源。可使用固定 Git 提交、内容可恢复的不可变快照或已有等价版本系统；仅 `main`、`latest`、活动 URL、绝对本机路径或手写“v1”不够。

用[目录指纹工具](../scripts/fingerprint.mjs)对实际交付资源目录计算 SHA-256，需要时用 `--expect` 与记录比较。它将相对文件名和文件内容纳入计算；CSS、JS、资产增删改名同样影响结果，不受目录搬迁影响。

指纹只检测内容变化：

- 不保存旧文件，必须另用 Git/快照保留确认时的完整内容。
- 不检查 HTML 能否运行，不识别用户，不证明反馈真实，不自动计算场景覆盖。
- 不包含目录外依赖和远程动态内容；先把可交付依赖纳入包，或另行锁定并记录其边界。
- 不应计算源项目全仓库或 node_modules；计算实际交付的原型资源。确认记录和命令输出放在目录之外，防止指纹包含自身记录。

原型修改后先看差异。视觉/交互/场景变化使受影响认可需要重新对齐；纯内部调整也必须记录新内容与旧确认的关系并验证等价，不能悄悄冒用旧摘要。旧确认绑定旧内容，新的证据/用户决定另记；必要时保留现有确认版本和一个明确候选，不堆多个互相竞争的“最终版”。

发现原型缺陷、业务冲突或无障碍问题时说明并修正，不把“原型优先”解释为必须复制已知错误。新的用户决定优先，受影响原型与文档同步。归档时保留基线和可复现入口，更新相对链接，不清理成仅剩截图或说明。

## 交给实施与验收

按[证据引用方法](design-evidence.md)传递“版本 + 文件 + 真实定位 + 场景”，需要时参考[完整源码示例](design-evidence-example.md)。

| 接收者 | 必须带入的依据 |
| --- | --- |
| `dev-spec` / `dev-ui-design` | 用户决定、确认范围、HTML/CSS/JS 逐节定位；补充业务规则与未表达边界，不文字重定义效果 |
| `dev-plan` | 每个切片对应的原型页面/状态/操作、确认记录、版本及可观察验收；未确认部分不能伪装为已具备前置条件 |
| `dev-build` | 打开实际原型及资源，复核确认是否仍适用；适配生产技术但保留已确认体验，接通真实能力 |
| `dev-review` / `dev-verify` | 同版本原型与当前产品的同一旅程、状态、视口、主题对照；单列真实 API/存储/外部副作用验证 |
| `dev-handoff` / `dev-archive` | 入口、完整资源版本/指纹、确认来源和范围、缺口、恢复办法；保留历史确认内容 |

原型是覆盖范围内可见效果的首要依据；说明文档解释意图和后台约束，任务清单安排工作。引用首页并让实施者自行猜测不够；截图不能替代可用的 CSS/JS。生产实现仍需验证权限、数据和真实副作用，不能把模拟通过写为产品通过。

实现偏离时指出具体差异及证据，修正实现或根据用户新的决定更新原型；不能改预期基线来让已有实现“通过”，不能因为任务都勾完就关闭尚未对齐的体验。复用原型组件/逻辑前按项目生产约束检查，而非机械复制演示壳。

## 规模与边界

- 新增或实质改变页面、导航、交互流程的 change，先用完整确认原型对齐最终体验；已有完整确认原型则复用，不重复阶段。
- 纯文案、无可见变化的内部重构或必要的紧急恢复，不为形式虚构 UI。说明实际不适用理由，继续原任务。
- 用户明确希望理解 API、CLI、状态机或后台行为时，生成 HTML 输入/输出和状态演示，沿用可用项目视觉语言，标明不是新增产品 UI。原型不能证明算法性能或服务真实性。
- 全新项目没有视觉基线时，先从用户已有参考和认可方向开始；确有重要未决方向时使用探索方法，不把采购示例的配色当通用默认。
- 只要求原型则交付原型及未决项；已经明确要求实施时，在相关确认充分后直接返回执行，不再询问实施/PR/合并等已经授权事项。

## 完成标准与常见失败

可交付原型应有真实可打开的入口，全部需求有明确去向，所有本次可视旅程可操作并可重置，项目风格有依据，模拟边界和实际检查如实记录。只有用户实际认可相应版本与范围时才称“已确认”；完成生成、完成自检、获得用户确认是不同事实。

| 失败表现 | 需要纠正什么 |
| --- | --- |
| 文档很齐全，直接开发但用户看到后完全不认同 | 对尚未对齐的可见效果先交付确认原型，不把文字认可等同于视觉认可 |
| 页面漂亮，按钮全是空回调或弹提示 | 接通模拟状态和完整结果，把取消/失败/恢复做成可操作路径 |
| 框架相同却换了导航、配色、密度 | 回到真实项目组件和样式来源，而非按框架刻板印象重新设计 |
| 用户确认后改 CSS/JS，却仍引用旧“v1” | 保留旧资源，计算新内容，定位受影响范围并重新对齐 |
| 把已确认 HTML 当可丢弃演示，只留下总结 | 保留完整基线，向实施传递源码和场景，而不是摘要 |
| 假装用户确认，或把模拟通过当后台成功 | 分别记录真实用户反馈、浏览器观察与生产能力验证 |

# 可视化意图确认

把已经理解的需求变成用户能看见、操作、指出偏差的 HTML。默认目标是确认本 change 的最终体验：覆盖完整需求闭环，保留用户实际认可的版本，再交给实施。文档解释这个版本的意图与边界，任务安排如何实现它。

## 选择当前工作

| 当前目标 | 读取与执行 | 结束时留下什么 |
| --- | --- | --- |
| 文档已收敛，要直观看到并确认最终效果；已有原型需要补全或修订 | [change 确认方法](references/change-prototype.md) | 可操作 HTML、实际走查、真实用户确认或明确待确认范围、固定版本 |
| 写设计说明或把确认结果交给规格、任务、实施与验收 | [原型证据与引用](references/design-evidence.md)；需要具体源码定位时读[完整示例](references/design-evidence-example.md) | 每部分对应的版本、文件、UI/CSS/JS 定位与场景 |
| 还有一个明确的未知问题，要用试验找答案 | [探索原型](references/prototype-method.md)，按问题选[界面变体](references/ui-prototype.md)或[逻辑演练](references/logic-prototype.md) | 问题、可重复试验和决定；不是最终体验确认 |
| 要低成本比较不同设计或行为方向 | [轻量方案比选](references/prototype.md) | 候选、实际观察、取舍与推荐 |

探索是可选分支，不是确认前必须重新做的阶段。已经明确的风格、布局和决定不再强制生成多个候选；探索结论进入同一 change，需要最终体验确认时回到确认方法。不要把探索的“一次性、少打磨”套用到确认原型。

## 从已有事实开始

完整读取本次来源、讨论、最终需求、规格、设计和约束；已有文档用真实路径引用，不为了形式再写一套。材料散乱或目标表达待整理时调用 `dev-intake`；存在证据不能替用户决定的产品取舍时调用 `dev-grill`。携带已有决定与记录位置，只解决影响当前产物的缺口，完成后继续原型任务。

检查实际页面、路由、组件、tokens、样式、图标、字体、截图及键盘/滚动/弹层习惯。技术栈名称不能证明视觉风格。沿用项目认可的布局、密度、配色和交互；需要补设计时调用 `dev-ui-design`，不凭个人偏好换肤。全新项目没有基线时明确说明，并按用户已有方向工作。

## 做到可以亲自体验

按每条需求检查入口、动作、状态变化、结果，以及适用的取消、返回、错误与恢复。真实长度的数据、空态、加载、禁用、权限反馈、长内容、主题和窄屏按本次范围覆盖，无法在 HTML 验证的后台约束引用规格并说明边界。

关键按钮、表单、列表、抽屉和导航必须产生实际的前端状态变化；成功提示不能替代列表/详情的结果更新。使用明确标注的模拟数据，提供自由操作、必要的引导演练和确定性重置。模拟发送、连接或保存不能连接真实外部写操作。

默认交付 `.agents/dev/changes/<日期-主题>/prototype/index.html` 和必要本地资源。简单场景用自包含 HTML；复杂场景可复用当前项目组件和构建工具，但要交付可打开的 HTML 入口、完整资源与可靠启动说明。临时预览链接和截图只作补充，不是唯一产物。示例包只演示证据定位，不作为项目默认视觉模板。

在可用浏览器中实际走通用户旅程并修复；检查同一页面、状态、视口、主题及必要键盘/焦点行为。不能把静态阅读、构建成功、按钮存在或子代理报告写成浏览器验证。工具不可用时交付可检查产物，明确缺少的验证；用户可以完成实际走查，不能由 Agent 补写不存在的结果。

## 用户确认与版本

先把可以体验的结果做完整、检查并交付，再请用户确认实际看到的范围。沿用[确认记录模板](assets/prototype-review.md)或项目已有记录，在原型目录之外保存入口、完整资源版本、场景、用户反馈来源与真实确认；版本与确认事实集中于已有 Markdown/Git，不另建流程 JSON、确认状态清单或审批引擎。用于业务模拟的 JSON fixture 不受此记录约束影响。

用户针对具体版本、具体范围的明确认可才是确认。Agent 自检、自己点击确认按钮、沉默、仅认可文字方案或笼统授权开发都不能代替它。已有同内容、同范围的有效确认直接复用；确实缺少确认时只暂停依赖该体验决定的实施，并继续不依赖它的已授权工作。

固定提交或保留的不可变快照应能恢复当时的 HTML 及全部 CSS/JS/图片/字体等依赖。需要校验内容是否改变时，使用[目录指纹工具](scripts/fingerprint.mjs)：

```text
node .agents/skills/dev-prototype/scripts/fingerprint.mjs .agents/dev/changes/<日期-主题>/prototype
node .agents/skills/dev-prototype/scripts/fingerprint.mjs .agents/dev/changes/<日期-主题>/prototype --expect <已记录的SHA256>
```

指纹不是备份，不证明用户确认或浏览器效果；不要把输出重定向进被计算的目录。资源改变时保留旧确认版本，核对影响并更新引用；影响体验的范围重新对齐，不能只改文件继续沿用旧确认。

## 向实施传递同一依据

- 用户最新明确决定优先；已确认原型决定其覆盖范围内的布局、信息层级、组件组合、交互和状态反馈。文档按节就近引用实际源码，不用文字重新解释成另一种效果。
- 业务规则、权限、数据一致性、性能、安全和未被原型表达的要求继续由规格约束。模拟成功不代表真实 API、数据库或生产能力通过；原型代码也不自动成为生产实现。
- 将入口、固定版本/指纹、确认记录、场景和实际 HTML/CSS/JS 定位传给 `dev-spec`、`dev-plan`、`dev-build`、`dev-review`、`dev-verify` 和 `dev-handoff`。任务清单不能覆盖已确认的交互效果。
- 文字、原型或实现冲突时定位来源和最新决定，修正受影响部分。不得把已确认原型降为“只是 demo”、改基线掩盖偏差，或复制已知缺陷却忽略规格约束。
- 长期保留确认版本及必要资源，随同一 change 归档；已有长期设计源可引用固定版本，不额外复制竞争的“最终版”。

纯文字小修或没有可见行为变化的内部维护不必虚构 UI。用户明确要用可视化确认 API、CLI 或后台逻辑时，用 HTML 呈现输入、状态和结果，标明这是行为演示而非新增产品界面。

交付时说清：打开哪里、怎样走通完整场景、实际验证了什么、哪些范围得到用户确认、哪些仍未确认、实施接下来必须对照哪个版本。只请求做原型时交付到这里；已有实施授权且确认充分时返回原任务继续。

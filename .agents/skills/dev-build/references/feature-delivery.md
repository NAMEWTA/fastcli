### 功能开发

对照目标选择设计、实施和验证方法。按当前任务及项目约定核实审查所需的证据。

1. 核对本次权威行为契约与适用的原型确认前提，携带确认版本、范围和具体页面/状态；需要可视化对齐但缺少有效确认时交 `dev-prototype`，只推进不依赖该决定的部分。读取受影响子系统的真实入口和行为；尚不理解相关模块时调用 `dev-learn`，携带本次变化目标，取得入口、调用路径与证据后继续当前实施。
2. 存在实质接口、状态或模块取舍时调用 `dev-architecture`，传入同一契约和已有决定，取得候选结构、接口与取舍后返回当前切片；已有明确局部形态的小改动直接实现。
3. 非平凡多步骤工作检查以下四个维度，只记录实际影响执行的决定；单文件或没有并行机会时用一句话说明即可，不建立空待办。
   - **阻塞性前置步骤。** 在扇出之前完成门禁。
   - **独立工作流。** 不重叠的文件、服务或层可以并行；共享写入必须串行。
   - **共享可变状态。** 默认拆分目标（**先隔离共享状态** 工程原则）。只有真实不变量要求时才串行。
   - **最小安全拆分。** 按实际依赖和验证成本确定切片范围。
4. 先命名数据形态和组织结构：用状态机替代分散布尔量，用表或注册表替代重复分支，用类型模型替代跨文件形状假设。选用分工且存在独立可写范围时，给实施者明确文件路径、契约、数据结构和成功标准。实现有多种重要有效形态，如错误处理、抽象层或验证结构时，按 `dev-parallel` 的候选方案分支独立探索并交叉评判。没有并行工具或拆分收益时，直接实施并在完成后另做复核；不能伪称独立审查。不要通过等待嵌套代理的“待命”回复提前结束。注释按 `dev-writing` 的技术写作规则，只说明非显然原因。做精准修改；对依赖代码先读取当前真实版本。共享原语改进同步到所有相关消费者，并验证每个受影响的接口。提交按用户授权与项目流程进行。
5. 有确认原型时，对照相同状态、视口和主题验证实际布局、交互和反馈，另验真实后端与副作用；原型的模拟结果不等于生产行为证据。在匹配的界面上验证。“无结论”或在错误界面验证都不算通过，必须指出。
6. 按可验证单元组织实现和提交，每个小单元完成后验证再继续。需要 PR 堆叠时按真实依赖排列；只有实际分支状态需要且授权覆盖时才变基，保护已有用户工作，不为小改动强制整理提交。
7. 设计有争议时，交付前调用 `dev-review` 的对抗审查方法，传入争议、当前差异和已有证据。
8. 交付目标包含 PR 时调用 `dev-deploy` 的 PR 交付分支，携带当前提交与有效验证证据；否则按当前授权的提交或交付方式收束。

采用集中协调的分工时，代码耦合工作（一个功能、一次迁移）交给单一负责人，检查点直接放在其任务中。负责人在阻塞阶段结束后自行扇出。父级扇出用于产出独立成果的切片（审计、跨子系统调查、竞争性实验）。在阶段边界重写检查点。创建新的负责人，不要串联中断。

**回复：** 构建了什么、选择了什么及原因、吞吐检查点、开放决策。设计替代方案用表格。

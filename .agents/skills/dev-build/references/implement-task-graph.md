# 按任务图实现

读取现有规格、计划和实施票据。计划给出共享上下文、DAG 和整合终点，票据给出实际执行契约。单节点计划按同样方法接手。

对 `dev-plan` 产出的计划，以链接的本地 Markdown 票据为准。接续旧任务时沿用实际记录，外部跟踪器按已有约定和授权使用。

目标是按规格完成所有工单，并在实际组合版本验证整体行为。沿用约定的交付分支和授权，关闭外部工单须有授权。

这些工单不是步骤列表，而是一张具有阻塞关系的**任务图**。前置产物已就绪的工单组成**工作前沿**。

## 通用步骤

1. 从计划读取共享契约、环境与交付约定，打开票据及实际进度，核对规格、有效的原型确认以及各条直接依赖的必需产物。新计划出现缺失引用、循环或与票据不一致时交回 `dev-plan` 修订有问题的部分；已有有效且独立的工作按原契约继续。
2. 在当前执行位置核实实际路径、提交或可访问产物后选取可开工的票。没有并行授权或写入和资源无法隔离时顺序处理可开工项；有条件时可分配互不冲突的票。验证行为和调用方，在原票或已有进度标状态，实际结果更新 `evidences/` 内同名 `.md`。按 `dev-verify`（证据存放）传入目标项目 `temp/dev/` 的运行目录，不在独立检出误起新的记录根。关键产物可用后重算前沿，暂时为空时核实缺少的输入。
3. 对组合版本运行适用的验证与审查，按实际交付目标返回结果。项目要求独立复核时，核实来源和对应版本。具体分工按本次任务、项目约定与当前工具确定。

## 已选择逐工单隔离实施时

下面展开每项使用独立工作树、汇入同一整合分支的做法。采用此分支时，每个子代理启动使用新的上下文窗口。

与子代理之间的通信应当稀疏。主要通过**上下文指针**通信：指向规格、工单、研究笔记和先前提交。不要重复已经可以通过指针获取的信息。

根据当前执行主机可用资源与已有预留，在资源和工具共同上限内让**实施子代理**后台推进。每次新派发先预留，超额可开工项排队；资源等待不增加假的 DAG 依赖。

### 隔离实施步骤

1. 按通用步骤读取计划、规格、原票和实际进度。把票及其直接依赖产物的可访问位置传给实施者，开工时核对产物在实际工作树、提交或环境可用。有适用的确认原型时，同时核对资源版本、真实确认范围与各任务的页面和状态引用。缺少有效确认时，依赖它的工单由 `dev-prototype` 补齐前提。

2. （可选）使用一个**探索子代理**完成工单需要的探索，例如相关代码文件或外部文档。按 `dev-plan` 的研究方法保存 Markdown 笔记：已有研究按真实位置引用，新增单项研究可用当前变更目录的 research.md，多项独立研究各写 research/<topic>.md。交接时提供后续实施者实际可读的指针；隔离工作树无法访问时由协调者交付对应文件，不让多人覆盖共享记录。这样**实施子代理**就能专注于实现，而不是探索。

3. 创建整合分支。已授权创建 PR 时，在第 5 步第一次合并且有领先目标分支的提交后创建草稿 PR。按授权链接可访问的规格与工单。会触发外部事项关闭的引用须有相应授权。

4. 每个工单使用一个实施者的独立工作树和分支，由 `dev-worktree` 按已确认的整合分支基线创建或接手。每个实施者都应：
   - 开始前核对实际路径、分支和基线，已有工作按真实状态交接；
   - 明确工单契约及适用的原型入口、确认版本和场景；接收者必须能访问同一资源，不能只给临时预览 URL。按目标与风险选择实现方法；适合测试先行时使用`dev-tdd`（测试驱动方法），取得真实验收证据；
   - 交回最终提交、基线与验证结果，结束对自己的分支的写入。与最新整合分支的组合验证由集成者负责。

5. 同一批工单交回后，由一位集成者调用 `dev-worktree`，依次将完成的工作合并到直接父分支并验证本批整合结果。

6. 如果这改变了可处理工单的**工作前沿**，先核实退出实例、释放或保留的资源，再在当前预算内启动下一批**实施子代理**；集成树、构建和测试也占用同一预算。

7. 所有工单完成后，对整合分支按本地 `dev-review`（两轴审查）。用一个新的**实施子代理**核实代码审查问题，修复已确认且属于本次范围的问题。

8. 如果存在草稿 PR，将其标记为可供审查。否则按当前授权和跟踪器约定标记完成；关闭外部工单须有授权，并报告整合分支。

9. 由 `dev-worktree` 核对本次检出的合并和使用状态，在授权范围内完成清理。

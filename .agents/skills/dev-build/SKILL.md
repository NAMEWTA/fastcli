# 按规格实现

以用户目标、行为规格和适用的已确认原型定义结果，以代码实现结果，再取得风险相称的行为证据。从前置产物已就绪的任务开始，按可验证小单元推进，明确所有权并在同一交付面验证。

先明确本次行为契约和关键设计，再选择最有用的反馈方式。用户要求测试先行，或稳定的公共接口与快速测试能降低风险时，调用 `dev-tdd`，逐个完成失败测试与最小实现的红→绿循环；完整测试方法只在该技能维护。本技能负责实现切片和集成，不复制测试教程。也可以按规格直接实现后验证；不为低影响修改增加形式化流程。

实施主线见[功能交付](references/feature-delivery.md)，行为保持型修改见[重构](references/behavior-preserving-refactor.md)。接手已有票据计划时，包括单票计划，按[任务图实施](references/implement-task-graph.md)读取计划和对应票据。明确的单项实施或用户直接给出的可执行单票可沿用现有记录直接开始。

## 开始或恢复

读取规格、已有计划、原票据、实际进度和影响本次代码的项目规范。复核最新代码、分支和未提交改动，保留用户与其他任务的工作。恢复会话时，以实际工作树、提交和前置产物复核现有进度。

没有正式 spec 的小任务，先在现有记录中写清目标行为、范围和验收即可。缺失会改变产品目标或数据语义的决定时，只阻塞相关部分，不擅自猜成定案。

明确故障的调查修复以 `dev-debug` 为主，性能指标改善以 `dev-benchmark` 为主，显式测试先行采用 `dev-tdd` 方法。当前已在实施的任务复用这些方法与证据，不因为换用方法而重新规划或另开任务。

涉及新的可见布局、交互或用户明确要求可视化对齐时，实施前读取 `dev-prototype` 产物：原型入口、资源版本或内容指纹、`prototype-review.md` 中的实际用户确认与范围，以及本切片的页面/状态和 HTML/CSS/JS 定位。确认内容已变化或范围未覆盖时，仅让依赖该体验决定的部分返回 `dev-prototype`；已有有效确认不重问。文字规格齐全、实施授权或 Agent 自己点过页面，都不能替代用户对具体原型的确认。纯文案小修和没有新可见交互的内部重构不强制建立 UI。

已确认原型规定可见效果，业务规格补充权限、数据、性能和真实副作用。原型中的模拟成功不是后端完成证据；不要修改原型或放宽规格来迁就实现偏差。需要探索未决问题时也调用 `dev-prototype` 的探索分支，不在本包维护第二套原型方法。

新增工作记录统一使用 `.agents/dev/changes/<YYYY-MM-DD-slug>/`。进展记在原票或 `progress.md`；验收更新 Change 的 `evidences/` 内与原票完全同名的一份 `.md`。运行原件按 `dev-verify`（证据存放）写项目根 `temp/dev/`，不随 Git 提交。发现票据依赖或计划索引有误时由 `dev-plan` 核实并修订受影响的记录。

## 从前沿推进

以票内的直接依赖和必需产物判断可开工项，使用计划中的共享上下文与整合安排。每取得或整合可用前置产物后重算前沿。按当前授权和隔离能力执行，并在实际组合版本核对整体行为。

实际并行写入前明确各项边界和共享状态的写入归属。派发 Agent、安装依赖、构建、启动测试 worker 或浏览器前，复用 `.agents/dev/context/environment.md` 或已有权威位置中仍适用的环境与资源记录；缺失或过期的部分按实际执行主机核对。结合已有预留和工具上限分配名额，无名额时排队，恢复与负载变化时复测，不让每张票重新分配全机余量。

需要代理协作时，按 [委派与整合](references/delegation.md) 提供目标、契约、可写边界、依赖和完成证据。优先给文件与提交指针，不复制整段上下文。不同任务可用独立上下文和工作树；工具不可用时顺序完成同样的工作，不把工具依赖变成阻塞。

## 实现一个可验证单元

1. 确认切片的输入、行为、数据形状和成功条件；有确认原型时按相同页面、状态、主题与视口实现，沿用其版本和确认范围。
2. 按现有约定推进一个行为。非平凡设计先确定接口与所有权；选择测试先行时，先观察行为测试因尚未满足契约而失败，再写最小实现使其通过。已有设计与证据足够时直接实现。
3. 保持范围清楚。新发现若阻塞本次目标，纳入并说明；无关改进记为后续项。
4. 选择能证明该行为的最便宜充分检查，核对当前实现的实际结果。重要回归可在实现前用测试锁定，也可在实现过程中补齐；低影响修改不为数量添加测试。
5. 记录实际结果、产物和仍未验证的部分，再推进下一单元。

验证入口必须匹配交付物：UI 打开页面并操作相关状态，CLI 实际执行，服务调用接口，存储检查写入后重载。类型检查、构建和静态审查各自有价值，但不能证明它们没有观察的行为。

给已有正确行为补测试时，保持产品行为不变，用现有公共接口验证契约；需要检验测试敏感性时使用隔离故障注入，不为满足红绿形式增加产品改动。

遇到失败时依证据排查。被证据否定的试探性修补应撤回，不留下“可能有用”的代码。故障调查调用 `dev-debug`，传入当前切片、失败证据与预期行为；修复验证后返回原切片，不另开计划。

## 构建可操作界面

用户明确要求按钮、状态面板或机器人操作页面时，按[完整操作界面方法](references/action-ui.md)实现前端、服务端、真实 webhook 接入与验证，并用[接口约定](assets/action-contract.md)固定允许的动作、身份校验和失败结果。复用已有设计系统；密钥只留服务器，HTTP 接收成功与业务完成分开验证。查看进展本身不触发构建，按钮也不扩大动作授权。

## 整合与复核

先阅读实际 diff 和行为产物，再接受实施者的完成报告。需要回合并到直接父分支时调用 `dev-worktree`。在途 Git 冲突调用 `dev-merge-conflict`，沿用当前契约及受影响接口的检查。

分开审查两件事：实现是否满足规格，是否符合项目规范。较大工作可用独立审查者；也可在新一轮上下文中自行审查。调用 `dev-review`，复用当前规格、差异与行为证据。

检查结果绑定具体工作树或提交。代码后来变化时，判断原证据是否还覆盖当前交付；受影响的验证重跑。不要重复已经充分证明且未受影响的检查。

## 持续到授权的交付点

按照用户要求和项目流程提交、推送、创建 PR 或继续部署。外部动作只在已有授权覆盖时执行；用户已经授权的步骤直接完成，不反复问是否继续。没有被要求的 PR 评论、issue 关闭或团队通知不自动发送。

达到完成点时明确：

- 哪些规格行为已实现，证据在哪里。
- 哪些验证已运行，哪些因环境限制尚未完成。
- 实际提交、远端、PR 或部署状态；排队、配置成功和执行成功分开。
- 下一步是否属于本次授权范围。

若本次目标包括部署，代码完成只代表进入部署阶段，调用 `dev-deploy`。整体验收通过且达到约定终点后，由 Change 负责人写唯一的 `evidence.md`，引用各票同名报告，再交 `dev-archive` 收尾。只负责切片时更新本票报告并交回，不写整体验收。

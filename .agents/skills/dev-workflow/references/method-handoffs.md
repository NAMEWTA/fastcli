# 按任务调用完整方法

总入口保留任务选择、执行纪律和协调；保存交接、接续和明确暂停由 `dev-handoff` 负责，下表的方法本体由对应技能维护。读取其 `SKILL.md`，再按分支读取完整资源，不从标题猜路径，不复制正文到当前包。

## 调用与返回

1. 先明确当前负责人。传递用户目标、当前阶段、权威行为契约及各决定的记录位置、已有计划、适用原型与确认版本/范围、代码版本、证据位置、授权边界以及本次所需产物。
2. 被调用技能只解决当前问题，在指定位置补充自己的结果，其他位置保留引用。契约可以在已有 brief 或 spec 中原地完善；已有访谈、基线与设计不重做，对当前代码、环境和范围仍有效的测试证据直接复用。需要进一步方法时可以继续调用其他技能。
3. 返回产物、实际验证、剩余问题与下一步。当前负责人整合后恢复原任务，不让子方法接管一个无关的全流程。
4. 同一问题已经处于某技能执行中时，不再次递归调用它；带着新增证据继续该次执行。技能协作可以成环，任务调用不能空转。
5. 无专用技能调用 API 时，读取已安装的入口并在当前执行上下文应用方法；有子代理时可以委派，但不得虚报独立性。依赖缺失时报告具体名称和安装缺口，继续不依赖它的工作，不用摘要冒充未读取的全文。

## 执行路线的归属

| 当前目标 | 负责技能与完整方法 | 返回或终点 |
| --- | --- | --- |
| 撰写或发布可认领 Issue、修订正文、追加评论 | `dev-issue` 的撰写与 GitHub 操作方法 | 完整内容、权威记录位置、真实远端身份与回读结果；只要草稿时交付草稿 |
| 整理散落材料、目标与缺口 | `dev-intake` 的需求整理 | 有来源的开发请求与下一步 |
| 解决尚未确定的产品取舍 | `dev-grill` 的决策访谈 | 指定记录中的已确认决定与剩余分歧 |
| 补全独立实施与验收所需约定 | `dev-spec` 的行为规格与实施简报 | 同一份充分的权威行为契约 |
| 改写待执行请求 | `dev-sharpen` 的请求改写 | 可使用的提示词，不自动启动实现 |
| 对报告分类、查重、分流 | `dev-issue-triage` 的报告分诊 | 依据已有证据的分类与去向，不扩张成复现 |
| 调查机制或选择 | `dev-learn` 的调查方法；历史动机调用 `dev-why` | 有引用的解释、建议及未知 |
| 复现或修复功能缺陷 | `dev-debug` 的缺陷修复 | 同路径复现、根因、修复证据 |
| 测量与优化性能 | `dev-benchmark` 的性能问题 | 同负载基线、修复与测量 |
| 持续优化指标 | `dev-benchmark` 的持续优化 | 试验日志、保留/回滚结果 |
| 活进程取证 | `dev-benchmark` 的运行时取证 | 机制证据，不自动修改生产 |
| 已有轨迹取证 | `dev-benchmark` 的轨迹取证 | 产物与源码映射 |
| 实施新功能 | `dev-build` 的功能交付 | 已验收切片 |
| 实施行为保持型重构 | `dev-build` 的重构方法 | 不变量与前后行为证据 |
| change 可视化确认 | `dev-prototype` 的确认方法，沿用 `dev-ui-design` 提供的项目设计规则 | 可交互 HTML、走查与真实用户确认记录；成为体验实施依据 |
| 探索性原型 | `dev-prototype` 的探索方法；逻辑/UI 分支按需展开 | 实验证据与设计决定，不能自动成为最终确认基线 |
| 视觉一致 | `dev-verify` 的视觉等价 | 对齐证据与剩余差异 |
| 技能编写 | `dev-personalize` 的技能编写方法 | 完整入口与真实场景检查 |
| 稳定个人偏好提炼 | `dev-personalize` 的偏好提炼方法 | 来自授权记录的偏好证据与技能修改 |
| 选择属性检查工具或维护模型 | `dev-formal-verify` | 带假设、边界及代码映射的检查结果；生成技能采用 `dev-formal-verify-<area>` |
| 展示已有 TLA+/TLC 模型与结果 | `dev-statechart` | 兼容模型的状态图、反例和代码回放证据；JS 模型使用自身兼容的展示方式 |
| 盲测评估 | `dev-review` 的评测方法 | 隔离结果与判断依据 |
| 跟进 PR | `dev-deploy` 的 PR 跟进 | 状态检查或可合并结果 |
| 验证后落地 | `dev-deploy` 的验证后落地 | 已授权连续通过部分的合并结果 |
| 自主执行 | [自主执行](autonomous-execution.md) | 达到判据或真实阻塞 |
| 编排多个已有 Change | `dev-program` | 批次计划、当前可做项与整体完成条件 |
| 已选择集中协调多个执行者 | `dev-parallel` 的多执行者项目协调 | 多任务集成与进度证据 |
| 独立 PR 自动队列 | `dev-deploy` 的独立 PR 队列 | 按授权验证并合并 |
| 堆叠 PR 队列 | `dev-deploy` 的堆叠 PR 队列 | 待用户落地的已验证堆叠 |
| 接手任务 | `dev-handoff` 的会话接续 | 已复核恢复点，返回当前执行阶段 |
| 安全暂停 | `dev-handoff` 的安全暂停 | 明确暂停后的可恢复现场 |
| 实施计划与多阶段交付 | `dev-plan` 的垂直切片与多阶段计划 | 本地票据、DAG、共享上下文与组级整合验收 |
| 创建、接手、合并或清理 Git 工作树 | `dev-worktree` | 实际检出、父分支合并证据或授权范围内的清理结果 |
| 处理正在发生的 Git 冲突 | `dev-merge-conflict` | 已核对的解决内容、验证证据和未决项 |
| 创建 PR | `dev-deploy` 的 PR 准备 | 真实 PR 与行为证据 |
| 指定环境部署 | `dev-deploy` 的环境部署 | 实际制品、服务入口、业务验证与发布记录 |

仅保存开发上下文或准备跨会话交接时，调用 `dev-handoff` 的交接方法，返回交接文档和接收提示。保存本身不要求停止、启动新代理或重跑上述路线。

调用 `dev-issue` 时传入目标仓库、创建/更新/评论操作、已有事项身份、权威规格或票据、证据与发布授权。它按缺口调用需求、规格或计划方法后收回结果；已有本地票据的正文、阻塞边和实施进展仍在原处维护。Issue 所需的自包含内容和来源版本由发布正文表达，完整写入方法归 `dev-issue`。

## 实施中的典型协作

`dev-build` 实施切片时发现故障，调用 `dev-debug`，携带当前失败和预期行为。诊断发现适合且已选择的测试先行回归入口时，调用 `dev-tdd` 的六步缺陷回归，不转入新功能测试路线。修复后回到原场景，由 `dev-review` 检查契约与质量；真实入口证据尚不充分时再调用 `dev-verify` 补验，然后回到原切片。用户要求 PR 交付或环境部署时，分别进入 `dev-deploy` 对应分支；收尾由 `dev-archive` 保留长期知识。所有阶段引用同一变更目录与权威记录，不复制计划、重建基线或重复审批。

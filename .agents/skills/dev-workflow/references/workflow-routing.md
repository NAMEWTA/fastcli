# 需求到实施的阶段衔接

用于从尚未成形的想法逐步形成可实施行为。当前阶段已明确时，从对应阶段继续。

本文使用功能名称标识阶段方法，不要求安装同名技能。按入口已经选定的目标读取需要的阶段；已有共识、规格、任务和证据直接复用，工作目录只决定记录位置。

用户要求的是可认领 Issue、Issue 正文修订或增量评论时，直接由 `dev-issue` 负责相应交付。它按缺口借用下列方法，完成后返回 Issue 任务；仅要求 Issue 的任务不进入后续实现、PR 或部署。

**流程**是按当前缺口选择技能的路径。下方主流程说明从想法到交付可能需要哪些结果，接入路径说明怎样从已有工作继续；各阶段已有充分产物时直接复用。当前负责人始终保留目标和集成责任。

## 主流程：想法 → 交付

从未明确的想法开始时使用下列路径；规格已清楚的任务沿用原规格，并核对相关体验确认是否已满足，再从当前阶段继续。

1. **整理材料并解决必要决定。** 输入散落时先由 `dev-intake` 整理来源、事实、目标、范围和缺口。存在会改变结果的未决产品取舍时，再调用 `dev-grill` 的 `逐轮追问`；其 `记录式需求澄清` 与 `需求访谈` 使用相同访谈方法，只在记录需求上不同。已有决定充分时直接核对实施前提。在工作目录中查阅已有术语表与 ADR，新增决定沿用调用方指定的记录位置，长期语义由知识维护方法按需引用或沉淀；没有工作目录时在对话中保留结果。文字共识仍不能代替用户要求的可视化确认。
2. **分支：所有问题都能在对话中解决吗？** 如果某问题需要可运行的答案，例如状态、业务逻辑或必须亲眼看到的 UI，就绕道原型，需要转移时在往返两端用 **`交接`** 连接。原型与生产代码隔离。更换宿主、目录或实际需要独立会话时用 `dev-handoff` 准备交接；同一会话可直接运行原型并带回证据，参见阶段边界：
   - 需要跨会话时先用 `dev-handoff` 保存状态，再基于该文件继续；否则在当前会话保留原始问题。
   - 用 `dev-prototype` 的**探索分支**以一次性代码回答未决问题；探索结论不代替最终体验确认。
   - 将原型所得证据带回原需求；跨会话时用 `dev-handoff`，否则直接引用产物。
3. **核对行为契约与可视化效果。** 只有现有约定不足以独立实施、审查或验收时，才由 `dev-spec` 补齐；可在已有 brief 或 spec 中完善同一份权威契约，不为阶段名称另写副本。涉及新的可见布局、交互，或用户明确要求可视化对齐时，文档齐备后调用 `dev-prototype` 的默认确认分支：从当前项目取风格证据，形成覆盖完整旅程的 HTML、实际走查，再记录用户对具体版本与范围的确认。原型是可见效果与交互的首要依据，规格说明规则和未被模拟覆盖的约束，任务负责组织实施。已有有效确认直接复用；缺少或失效的确认只阻塞依赖它的工作。纯文案小修、无新可见交互的内部重构可沿用现有证据，不强制建 UI。
4. **分支：需要形成计划，还是已有可实施的工作？**
   - **需要实施计划、拆票或调整依赖** → 沿用现有规格与适用的确认原型。由 `dev-plan` 用 **`垂直切片`** 形成曳光弹任务，每项保存一张本地票据，写明阻塞依赖和所需产物，再在 `plan.md` 汇总 DAG、共享上下文和整合安排。即使只有一张票也保存计划。只要求规划就在这里交付。
   - **已有可执行票据计划** → 由 `dev-build` 读取计划及票据，按实际前置产物确定开工前沿。可用 **`按规格实施`** 逐项处理自包含票据，也可用 **`任务图实施`** 协调整个规格。有并行授权且工作树、写入边界与资源可隔离时并行推进，汇入同一整合分支。按窗口容量整理上下文，保留原票和实际恢复点。
   - **明确的单项实施** → 由 `dev-build` 在当前上下文运行 **`按规格实施`**，复用已有契约和适用证据。

   实施前先明确目标行为与验收，再按目标、风险和反馈成本选择规格推进、测试先行或直接实现。适合测试先行时使用 `dev-tdd`，每个循环处理一个行为。按规格和规范两轴审查单项差异及整体集成结果。

   工作以拉取请求交付时，**`PR 证据`** 塑造正文：能展示变化的最小视图、证明有效的前后证据，以及单向门还是双向门的判断。需要 PR 时调用 `dev-deploy` 的 PR 交付分支；另有环境部署目标时才执行该技能的部署分支。

5. **`迭代复盘`** 闭合循环。构建后，尤其过程偏离轨道时，由 `dev-archive` 回顾会话，建议改进智能体的**环境**：导航指针、自动检查、`两轴审查` 执行的编码规范、引导文件、工具。适合机械判断且收益覆盖误报和维护成本的错误，由 `dev-guardrails` 落实到类型、结构或已有检查；判断类经验保留说明与案例。下一轮构建沿用这些有证据的改进。

### 上下文卫生

追问、规格和任务尽量保留同一套原始思考；上下文仍足够时直接继续。接近实际窗口限制或任务已经自包含时，在阶段边界按本包阶段边界方法整理，使用宿主确实支持的压缩、清空或独立上下文。每项任务都应自包含，但不要求每次实施必须新开会话；无对应工具时用 `dev-handoff` 保留恢复点并继续。保存或压缩不等于暂停。`迭代复盘` 应在其所回顾的会话内、清空前运行；清空之后则指向该会话日志。

限制因素是**有效推理上下文**：模型仍能敏锐推理的窗口，阈值取决于实际宿主、模型及任务复杂度。如果在 `垂直切片` 之前会话已接近这个区间，不要在能力下降后硬撑；在最近阶段边界执行 `压缩上下文` 再继续，参见阶段边界。

## 接入路径

某种起始情况产生工作，再汇入主流程。

- **缺陷和请求堆积** → 先明确想得到什么。要撰写或维护可认领 Issue、追加评论时用 `dev-issue`；需要分类、查重和去向时用 `dev-issue-triage`；需要把材料整理成开发请求时用 `dev-intake` 的 **`输入分诊`**。要求复现、定位或修复时进入 `dev-debug`，符合可信报告管道与 UI 控制前提时可用 `dev-issue-fix`。同一份 Issue 可以服务不同目标，来源格式不决定技能。

  `垂直切片` 产出的任务已经可执行，直接由 **`按规格实施`** 接手；没有新的证据或路由需要时不再分诊。

- **要修复某个东西** → **`根因诊断`**。用于难题：第一眼看不懂的缺陷、间歇性失败、两个已知正常状态之间引入的回归。它在建立**紧凑反馈循环**之前拒绝凭空推理；循环是已能因**这个**缺陷变红的一条命令。存在正确接口时先用回归测试锁定故障，再依据证据修复；真实运行复现更合适时沿同一路径验证。修复后在同一会话运行 **`迭代复盘`**，追问什么本可防止缺陷；如果真正发现的是没有合适接缝来锁住行为，就交给 **`架构改善`**。

- **巨大而模糊的工作：全新项目或大型功能，一个会话装不下** → **`复杂决策规划`**，这里认知要求最高的流程。从当前位置到终点的路还不可见时，它在事项跟踪器建立由**决策任务**组成的**共享地图**，逐个解决，产出**决定而非交付物**，直到迷雾退去、路径清楚。**`记录式需求澄清`** 打磨一个会话能容纳的想法，复杂决策规划 处理装不下的想法，速度更慢、内容更密集，所以只在这种情况使用，不用于范围明确的功能。

  地图清晰后先核对现有决定能否作为行为契约，有缺口时由 `dev-spec` 在原记录补全。完成适用的可视化确认，再按第 4 步选择出票和组装计划，或接手已明确的实施。沿用原决定及其链接。

## 代码库健康

不是功能工作，只是维护。

- **`架构改善`** 在有空时运行，让代码库持续适合智能体操作。它发现**加深机会**；选中一个就**生成想法**，可从 `记录式需求澄清` 进入主流程。它是寻找候选对象的勘察；下方 **`模块设计`** 则是设计选中对象的工作台。

## 底层词汇

领域词汇和模块设计作为基础参考，各自维持一个事实来源。当问题是**用词**而非流程时直接使用，或者让上层技能加载。

- **`领域词汇整理`**：打磨项目的**领域**语言，质疑模糊术语、解决一个词做三件事的多义情况，例如 account，把难逆转的决定记录为 ADR。它是 `记录式需求澄清` 用来保持 `.agents/dev/notes/glossary.md` 及其指向的已有术语表 纯粹的主动实践。
- **`模块设计`** 是设计模块**形状**的深模块词汇：模块、接口、深度、接缝、适配器、效能、局部性；大量行为位于清楚接缝处的小接口后面。规格实施、测试驱动开发和架构改善都使用这套语言。

## 阶段边界

**阶段**是会话中的一块工作，例如追问、实现、质量检查。两个阶段的**边界**有五种选择；在它们之间选择，是整张地图里最模糊的决定：

- **继续**：留在当前会话。无成本、无损失。
- **`清空上下文`**：当这里的内容对下一步无关时清空窗口。
- **`交接`**：由 `dev-handoff` 写一份可移植 Markdown，用于**更换宿主**、**更换目录**、交给**同事**、在**阶段中途**分出旁支任务，或按用户要求保存稍后继续的开发上下文。换来的是可移植性与可恢复记录；仅保存时仍可在当前会话继续。
- **子智能体**：把范围紧凑的任务交给独立窗口，拿回报告。
- **`压缩上下文`**：使用宿主真实提供的压缩能力，以整理后的上下文继续。它是**默认落点**，位于决策树底部，而不是首先使用。

阅读 [phase-boundaries.md](phase-boundaries.md)，查看有顺序的决策树：五个问题、每个分支背后的理由，以及为什么一手资料的损失成本使**继续**成为首先应排除的选项。常规整理在边界作决定；用户明确要求保存或暂停时，调用 `dev-handoff` 对应方法，不等待阶段结束才响应。

## 可独立执行的操作

完全脱离主流程。

- **`需求访谈`**：解决尚未明确的产品决定。仅在对话中讨论时不要求本地记录；需要项目持久化时使用 `记录式需求澄清`，复用已有术语和决定。两种形式都只追问未解决、会改变结果的分歧，不重复访谈已有清楚规格的任务。
- **`逐轮追问`** 是 `dev-grill` 的访谈基础方法：轮次、前沿、事实由智能体查、决定由你做。`需求访谈` 和 `记录式需求澄清` 是两个形式；`输入分诊`、`复杂决策规划`、`架构改善` 只有遇到尚未解决的产品取舍时才调用。被调用时沿用指定决策记录，完成后回到原负责人；想直接访谈时使用 `dev-grill`。
- **探索性原型**由 `dev-prototype` 的探索分支负责，是回答一个设计问题的小型实验：状态模型是否合理，或候选 UI 如何取舍。探索代码按该分支规则隔离保存，答案与证据回到原任务。**确认原型**则是文档收敛后、覆盖整个 change 的长期体验依据；HTML/CSS/JS 与确认记录随 change 留存并供实施引用，不适用探索方法中的可丢弃或主分支外保存规则。两种用途都不能把模拟成功当成真实功能已实现。
- **`证据研究`**：把阅读调查委派给**后台智能体**，它基于**一手来源**研究问题，再在仓库留下一份有引文的 Markdown。它阅读时你继续工作。产出文件可带入 `记录式需求澄清` 的主流程，因为研究为思考提供材料，而不是代替思考。
- **`问卷收集`**：阻塞信息不在你脑中或代码库中，而在**别人脑中**时，写一份让对方填写的问卷。它是 `需求访谈` 的反向形式：不是就主题采访你，而是就**发送任务**采访你——发给谁、需要什么反馈——再把问题瞄准信息缺口。返回内容可作为 `记录式需求澄清` 或 `形成规格` 的材料。
- **`人工操作指引`**：用于只有**人**能做的步骤，例如配置基础设施、设置凭证或 CI 密钥、点击不熟悉的第三方控制台、执行一次性迁移或切换。它生成交互式 bash 脚本，逐个打开 URL、收集值、写入 `.env` 和 GitHub secrets，使操作流程不必每次重新向智能体解释。遇到确实只有人能完成的障碍时，先准备可检查步骤，再说明需要用户完成的具体动作；不要求一个不存在的自动调用技能。智能体能自己做的就自己做；这里用于人确实必须参与的情况。
- **`重新解释`**：纠正没有被理解的消息。可在任何技能内、对话中途使用，智能体会补上缺失上下文，以通俗中文和项目术语重新解释刚才的话。它是事后补救；`记录式需求澄清` 是事前解法，因为提早约定共享语言，就能防止术语突然出现。
- **`模块学习`**：使用当前目录作为有状态工作区，跨多个会话学习一个概念。
- **`智能体文档写作`**：编写智能体消费文档的参考，包括技能、AGENTS.md 和被指针引用的文档。

## 前置条件

先复用当前项目的任务记录和文档布局；没有时使用轻量 Markdown，不强制初始化外部跟踪器或复杂状态协议。

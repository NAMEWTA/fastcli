把聊天、文档、问题报告和附带改动的请求整理成需求简报，说明已有事实、目标、决定与下一步缺口。复用项目已有跟踪器；没有跟踪器时用本地 Markdown。下列角色用于理解已有跟踪记录和交接结果，不要求状态机、固定标签或迁移门禁。

先按用户要的结果分流：只需报告分类、查重、负责人或去向时交 `dev-issue-triage`；需要复现和修复时交 `dev-debug`，符合可信报告流程时交 `dev-issue-fix`；需要补足可独立实施的行为契约时交 `dev-spec`。本方法保留事项来源的阅读、整理和恢复规则，不另执行这些技能的完整方法。

如果仓库把外部拉取请求也视为需求入口，见事项跟踪器配置，来源整理也涵盖它们：**PR 是附带代码的事项**，采用相同的上下文阅读思路，差异在下文以“对于 PR”标明。裸编号 `#42` 应按跟踪器配置解析为事项或 PR。

仅在用户已经授权发布事项或评论时执行外部写入，复用项目披露规范；没有规范时可使用以下声明。读取或分诊本身不授权评论、关单或改标签：

```text
> *此内容由 AI 在分诊过程中生成。*
```

## 参考文档

- `dev-spec`（完整实施简报）：在原权威记录中补足可独立实施、审查和验收的行为契约。
- [范围决定](scope-boundaries.md)：`.agents/dev/notes/context/scope-decisions/` 知识库如何工作。

## 角色

两个**类别**角色：

- `bug`：某项行为损坏。
- `enhancement`：新功能或改进。

五个**状态**角色：

- `needs-triage`：维护者需要评估。
- `needs-info`：等待报告者补充信息。
- `ready-for-agent`：规格完整，可交给无人值守智能体。
- `ready-for-human`：需要人来实现。
- `wontfix`：不执行。

对于 PR，相同状态应结合附带代码理解：`ready-for-agent` 表示已有充分契约，智能体应在当前差异上继续下一步；`ready-for-human` 表示需要人工承接，是否可合并仍以实际审查与验证为准。

已有标签体系时，避免互相矛盾的分类和进展描述。遇到冲突先读取最新讨论与实际证据，修正本地简报；只有冲突影响目标且无法查明时才询问维护者。没有标签体系无需创建。

这些名称只帮助理解分支。复用已有跟踪器标签或自然语言描述；本地记录方法见 `dev-plan`（本地工作记录）。

处理结果可以是待评估、待补信息、可实施、需人工或不执行。报告者提供新证据后重新评估；维护者的最新明确意图和已授权范围持续有效。不要求按某个状态顺序流转。

## 调用

维护者用自然语言描述意图。先识别整理需求、报告分流还是具体处理，再选择负责技能。例如：

- “汇总这些事项里已经确认的需求与缺口。”由本技能整理。
- “看一下 #42。”可以是事项或 PR；结合上下文判断用户所需结果。
- “把 #42 移到 ready-for-agent。”沿用明确授权与已有判断，核对现有契约后按项目跟踪约定执行。
- “有哪些报告重复，该交给谁？”由 `dev-issue-triage` 分类、查重和分流。
- “有哪些需求已有足够信息，可以交给智能体处理？”由本技能汇总已有材料，契约缺口交 `dev-spec`。

## 展示需要关注的事项

需要汇总来源队列时，读取事项跟踪器的已有状态，按以下三组展示，各组旧的在前；需要重新分类、查重或分流时调用 `dev-issue-triage`，不由目录列表推断结论：

1. **无标签**：从未分诊。
2. **`needs-triage`**：正在评估。
3. **上次分诊笔记后报告者有新活动的 `needs-info`**：需要重新评估。

PR 在范围内时，把外部 PR 也放进这些组，每行标注 `[PR]` 或 `[issue]`。发现阶段只展示**外部** PR，跟踪器配置定义何为外部，因此协作者正在开发的 PR 不属于分诊工作。这个过滤只适用于发现阶段；明确指定的 PR 无论作者是谁都应分诊。

显示数量，并为每项提供一行概述。若用户要求浏览队列，供其选择；已指定目标时直接处理目标。

## 整理指定事项或 PR

1. **收集上下文。** 阅读完整事项或 PR，包括正文、评论、标签、作者和日期；PR 还要阅读差异。解析已有分诊笔记，避免重复询问已解决的问题。使用项目领域词汇表探索相关代码，尊重相关区域的 ADR。针对现状核对两项：其一，**已有实现检查**，按领域概念而不只按请求措辞搜索已有能力，并报告查过哪里及适用版本；如果已存在，记录已实现证据，整理处理建议，不能仅凭名称相同下结论。其二，**先前拒绝检查**，阅读 `.agents/dev/notes/context/scope-decisions/` 中相关记录，指出类似请求。跨报告查重由 `dev-issue-triage` 负责。

2. **提出下一步建议。** 说明来源中的已有类别与状态、相关代码情况、已确认目标和仍缺的信息。需要新的分类、查重或分流结论时引用 `dev-issue-triage` 的结果。用户明确要求先审建议时等待；已要求处理时，在既有授权内继续。

3. **核对主张的证据。** 任何追问前，先阅读可取得的代码、日志和已有验证，区分已确认、被反证和待验证。已充分且仍适用的证据直接引用。仅整理材料时不默认复现缺陷、检出 PR 或运行测试；需要运行证据且用户目标包括调查、审查或实施时，交 `dev-debug` 按报告者步骤复现，或交 `dev-review` / `dev-verify` 在合适检出中核对 PR 声称的行为。回收实际代码路径、运行结果与版本；细节不足说明具体缺口，不将“尚未运行”写成“验证失败”。

4. **补足真正缺失的信息。** 来源缺失做简短补问；存在证据不能替用户确定的产品取舍时调用 `dev-grill`，传入已确认内容、决策记录位置和本次未决问题，解决后回到来源整理。只有领域术语确有冲突时调用 `dev-architecture`；长期词汇与取舍在已有 glossary／ADR 中更新，简报引用其位置。契约缺少行为、接口或验收细节时交 `dev-spec` 补全原文，不机械再访谈或新建规格。

5. **保存与交接结果：** 只要求整理时交付来源简报、权威契约与决定的指针，以及下一步缺口。以下保留已有跟踪角色的结果含义；分类、查重与报告回写由 `dev-issue-triage` 负责，契约补全由 `dev-spec` 负责。发布、标签和关闭操作均以用户已授权对应外部动作为前提；未授权时保存为本地记录或待执行建议，不冒充已发布。
   - `ready-for-agent`：已有契约足以独立实施时引用它；存在缺口时用 `dev-spec` 的完整实施简报方法原地补足。有发布授权才回写该契约的引用或同步内容，不另维护一份竞争简报。
   - `ready-for-human`：结构与智能体简报相同，但说明为什么不能委派，例如判断取舍、外部权限、设计决定、人工测试。
   - `needs-info`：发布分诊笔记，模板见下文。
   - `wontfix`：关闭事项，评论内容取决于**原因**：
     - **已经实现**：代码库中已有此变更。指出所在位置；**不要**写入 `.agents/dev/notes/context/scope-decisions/`，该知识库用于记录被拒绝的请求，而不是已实现的功能。
     - **拒绝，缺陷**：礼貌解释，然后关闭。
     - **拒绝，增强**：写入 `.agents/dev/notes/context/scope-decisions/`，在评论中链接它，然后关闭，见 [范围决定](scope-boundaries.md)。
   - `needs-triage`：应用角色。如有部分进展，可选择评论。

## 快速覆盖状态

维护者说“把 #42 移到 ready-for-agent”时，沿用其判断和明确授权，按已有跟踪约定执行该角色修改，不重复索要确认。授权只覆盖所要求的动作，不自动添加评论或关闭。跳过已经完成的追问；需要交接时引用已有契约，确有行为约定缺口才交 `dev-spec` 在原记录中补足，未决产品取舍交 `dev-grill`。

## 待补信息模板

```markdown
## 分诊笔记

**目前已经确定：**

- 要点 1
- 要点 2

**仍需要你（@reporter）补充：**

- 问题 1
- 问题 2
```

把本次补充的事实放在“目前已经确定”下；已有决定与行为契约保留要点及其权威记录链接，避免成果丢失和重复维护。问题必须具体、可行动，不能只是“请提供更多信息”。

## 恢复先前会话

事项或 PR 已有分诊笔记时，先阅读，检查报告者是否回答了未决问题，再在继续前展示更新后的全貌。不要重复询问已解决问题。

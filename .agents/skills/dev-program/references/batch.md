# 从成员清单推进到整体验收

## 圈定目标

逐项解析用户给出的目录、Issue 或清单，读取权威 brief、spec 或等价记录，并核对当前代码、制品和已验证范围。只有请求覆盖全部活跃 Change 时才据此发现成员。重复引用合为一项，缺失或含糊的引用标明待核实范围。批次文档自身是入口。成员较多时逐项对回原清单，防止遗漏。

明确本地实现并验证、开 PR、合并或指定环境上线等实际终点。已有确认、决定和授权继续适用。批次沿用本次已经确认的任务约束，只把影响交付的条件与接续点记入批次记录。用户只要顺序或 Goal 文本时交付规划，已要求实施时继续推进。需要补一项规格就沿该成员的已有文档补充。

## 找出跨 Change 的交付物

站在消费方追问：现在开始哪一步会缺什么？向提供方核实产物、版本和取证位置。已满足的条件直接引用证据。只有确实影响先后的关系才写入批次计划。

| 遇到的关系 | 怎样安排 |
| --- | --- |
| 实现需要稳定的 API 或事件 | 指出字段、兼容约定及版本在哪里核实。契约可用后即可开发，真实联调另等可运行版本。 |
| 运行需要迁移、实现或制品 | 写出目标环境或基线以及核实方法。只在消费者确实需要该版本时安排等待。 |
| 共享测试租户、写入位置或发布窗口 | 标出需要错开的动作和释放条件。其他设计、实现和准备仍可推进。 |
| 某项体验或业务选择尚待确认 | 引用已有决定，明确受影响的场景。处理不依赖该决定的工作。 |
| 仅涉及同一模块 | 查调用链、读写对象和兼容性。找不到阻塞依据时可分别推进。 |

同一对 Change 可以在不同交付点互相提供输入。遇到 A 等 B、B 又等 A，先展开各自在等的动作和产物。若 A 的接口足以让 B 提供样例，A 再用样例完成联调，就按此顺序推进。若双方都必须先拿到对方尚不可用的实现，列出实际闭环，核对是否可用兼容层或已有样例打开路径。仍受阻时继续独立成员。

## 选择下一步与接续

列出当前具备输入的工作，并说明其余项等什么。实际派发前由批次负责人核对本机及用户指定远端的当前资源与已有占用，跨 Change 统一预留；成员和嵌套执行者不能各自分配同一资源池全部余量。依赖已满足但没有名额的动作保持排队，不改写 DAG；回收、恢复或负载变化后再评估。尊重用户给定的优先级，同等条件下先做能解锁后续工作或消除关键不确定性的交付点。单个 Change 内的切片与实现沿用其计划，按需使用 dev-plan、dev-build 和 dev-verify。

首次保存批次时写明已核对的成员和下一步。成员交付前置产物、阻塞变化、版本变更或准备交接时，核实结果并刷新批次接续点。写出当前成员及其进度入口、谁因哪份产物可以开工、谁仍在等什么。并行成员分别链接其片内进度。成员均已完成时，下一步指向尚待验证的组合场景；运行原件留项目根 `temp/dev/`。达到批次终点后指向组合验收；批次有独立 Change 时，更新其唯一的 `evidence.md` 并引用成员报告。保留可复用证据。例如接口字段发生变化，应检查消费该字段的实现和测试；使用独立角色模型的权限检查可沿用有效结果。

恢复时从批次记录回到成员的实际工作区、分支、PR 或制品。工作可能已经做完但尚未登记，也可能已有记录而代码已改变。先核实两者，再补记录或补工作。归档移动成员目录时修复批次引用。需要交接时让 dev-handoff 引用这份记录。

## 回到原始交付目标

逐项回读交付位置和有效证据，再在同一组合版本验证用户要求的跨 Change 行为。只要求 PR 时可在隔离的组合版本联验，报告各 PR 的实际状态；指定环境交付则核对该环境实际运行的制品。仍受阻时说明未满足的条件、影响和恢复所需输入。范围调整沿用用户决定，并保留原目标与调整依据。

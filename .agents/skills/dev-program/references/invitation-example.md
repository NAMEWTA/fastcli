# 示例：把邀请、邮件与权限一起交付

以下是示例批次在几个时点的判断。用户要求在本地跑通整条邀请流程。成员 A 交付邀请 API，B 交付邮件通知，C 交付权限校验，D 验证发送、收件、接受邀请与拒绝越权操作。实际计划中，每项名称链接到项目中已有的权威记录。

1. **首次编排。** A 可以确定事件字段。C 只使用既有角色模型，可立即实现。D 可以准备角色和测试收件箱。B 等待事件契约。
2. **提前解锁。** A 的契约测试固定了事件名和收件人字段。B 引用这个版本，用样例验证邮件生成。验证真实触发仍需等 A 的可运行版本。B 和 D 共用收件箱时，只错开发送与读取这段操作。
3. **事实发生变化。** A 更新了收件人字段，旧样例已不适用。核对 B 的消费代码、更换样例并重跑相关场景。C 的权限规则和输入基线没有变化，可复用其测试结果。
4. **中断后继续。** 文档还写着“待更新邮件”，但当前提交已有修正。读取实际差异并重跑该消费场景，确认有效后更新批次记录，转入 D 的联验。
5. **整批交付。** 在同一组合版本实际发送邀请，核对测试收件箱、接受后的成员身份，以及越权请求被拒绝且未产生邮件。记录组合版本和测试结果，逐项链接 A 至 D 的交付证据。若只能生成邮件而没有收到，报告未通过的收件步骤并继续定位。

可用于此例的 Goal 文本：

> 完成邀请 API、邮件通知、权限校验和整链联验四个 Change，按所附各项规格交付到本地验证通过。用同一组合版本证明授权用户能发出并接受邀请、越权用户被拒绝，给出对应证据。

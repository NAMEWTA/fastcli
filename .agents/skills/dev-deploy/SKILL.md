# 代码交付与环境部署

先确定用户要交付到哪里，再读取对应完整方法。代码交付得到远端提交、PR 或合并结果；环境部署得到指定环境中实际运行的版本及可恢复记录。分别报告实际完成状态。

## 选择交付分支

| 本次目标 | 使用的方法 | 完成依据 |
| --- | --- | --- |
| 已选用 PR 队列交付方法 | 独立项读[独立 PR 队列](references/autonomous-queue.md)，待审的依赖链读[堆叠 PR 队列](references/autopilot-stack.md) | 逐项核对实际基线、裁决和授权终点 |
| 创建或更新 PR | [打开 PR](references/pull-request-procedure.md)、[PR 证据与说明](references/pull-request-evidence.md) | PR 地址、目标分支、当前头提交与有效验证证据 |
| 跟进 CI、审查意见或合并 | [跟进 PR](references/babysit.md)、[验证后落地](references/verified-landing.md) | 当前头的检查、意见处理、真实合并或明确待决状态 |
| 按指定方式提交并推送 | 沿用项目 Git 流程，复用本次有效审查与检查 | 实际远端分支及提交；不强制创建 PR |
| 部署、升级或恢复环境 | 下文环境部署流程；按需读[项目部署](references/project-deployment.md) | 实际制品版本、业务入口验证及恢复记录 |

只要求创建 PR 或跟进 CI 时，直接处理代码交付，不要求提供部署主机、数据库迁移或回滚计划。两个分支都在任务范围内时，复用同一提交和已有证据，再核验目标环境；PR 已合并不等于服务已部署。

普通批量交付沿用每项 PR 的交付目标。发布前核对本任务要求的证据；需要独立复核时，将结论与实际拟交付版本对齐。

启动本地构建、测试或浏览器验证前，复用 `.agents/dev/context/environment.md` 或已有权威位置中有效的主机预算与预留。记录缺失、过期或执行主机变化时，按当前运行环境、可用资源和本次负载直接判断启动条件；托管 CI 的资源按实际运行器核对。只读查看 PR 状态无需启动这些负载。

## 交付代码或 PR

1. 固定仓库、基准与目标分支、待交付提交，以及本次授权终点。区分创建 PR、跟进检查、合并和直接推送；已有明确授权继续执行，不重复询问。
2. 读取当前差异、权威行为契约、审查结论和验证证据。代码、依赖、环境与覆盖范围仍匹配时复用结果；发生影响行为的变化时只补足相关检查。需要新增审查或运行证据时分别调用 `dev-review`、`dev-verify`。
3. 按表中方法创建、更新或跟进 PR。没有 PR 的直接推送任务沿用指定分支流程，保留远端已有提交。需要观察器时读取[本地工具](references/local-tools.md)，工具状态仍需与当前平台事实核对。
4. 按授权完成提交、推送或合并，随后读取远端分支/PR 的实际状态。目标只是创建 PR 时以可审查 PR 收束；目标包含合并时持续到真实合并或明确的阻塞。CI 成功、`READY` 或本地提交不能代替远端完成证据。

交付沿用各票同名验收报告。新增 CI 下载、日志或截图放项目根 `temp/dev/`，不随 Git 提交。若负责完整 Change，只在整体验收通过、达到约定的 PR、合并或上线终点后写根 `evidence.md`。需要创建、审计或清理工作树时调用 `dev-worktree`。PR 分支已有 Git 冲突时，在明确的分支所有权和授权下调用 `dev-merge-conflict`，再按 PR 交付方法核对最新头。

## 环境部署：固定本次发布

先读项目真实启动方式、现有部署配置与本次规格，不凭技术栈猜一个通用部署命令。

- 核实环境、账号或集群、主机、项目路径/命名空间、对外入口与实际权限；不能沿用上次聊天的生产目标。
- 固定源码提交及实际构建制品，例如镜像 digest、包版本或静态产物摘要。工作区有未提交更改时说明其来源，不能只写 HEAD 冒充制品版本。
- 确认用户授权覆盖的部署范围。已明确要求把此项目上线到此环境就持续执行；环境或权限仍不清楚时，先准备制品、计划、差异、迁移与恢复办法，最后只问缺少的关键决定。

## 环境部署：准备并执行

1. 读取真实构建、启动、健康检查、环境变量、持久化目录、依赖与数据库迁移。核对已指定目标主机的运行条件与本次部署峰值，包括旧、新版本并存期间的资源；已有观测不足时在该目标补采样，更新适用的既有记录。验证是当前制品的结果；此前版本的绿灯不能代替。
2. 比较环境现状与目标，保留已知可用版本和必要备份。区分“应用回滚”和“数据恢复”；有不可逆迁移时写明恢复前提与数据损失窗口，不假装一次镜像回退就能撤销数据库变化。
3. 采用现有发布工具和目录。项目部署权限只覆盖该项目及获准依赖，不隐式取得整台服务器的清理、升级或代理修改权限。
4. 执行可重复的准备、依赖检查、单一迁移执行、发布和切换。多环境/多主机逐个保留实际结果，不能宣称跨主机原子成功。
5. 在真实入口验证版本、健康及至少一条相关业务路径。授权内使用可识别的验证数据并清理；只看端口打开、进程存活或 CI 成功不算上线验收。
6. 有失败先保留证据、停止依赖失败结果的后续步骤，再按已批准的恢复方案处理。不得删除数据库或盲目重复有副作用的迁移。

按需读取 [环境与发布方式](references/environments.md) 和 [凭据、备份与恢复](references/secrets-recovery.md)。发布验证针对指定环境中的实际行为。开发方法不限制交付：使用已有行为检查、必要的部署探针与真实业务操作，选择能够证明当前制品的证据，不为凑覆盖率增加测试。

## 环境部署：保存运行记录

新增部署资料统一放在 `.agents/dev/deploy/<环境>/`；已有手册按真实位置查阅引用，不擅自移动实际服务或数据目录：

- `runbook.md`：当前入口、实际项目根、构建发布方式、数据目录、依赖、检查、回滚与凭据**引用**。使用 [运行手册模板](assets/runbook.md)。
- `releases/<日期-版本>.md`：本次版本、命令摘要、迁移、验证证据、结果与未完成项。使用 [发布记录模板](assets/release.md)。

普通文档只记账号用途、配置键和获取方式。项目明确指定本地 `env.md` 用于直接查阅登录资料时，按[项目本地凭据文件](references/secrets-recovery.md#项目明确选用本地-envmd)把实际值写入该文件，并单独报告写入结果；没有显式指定则沿用现有凭据保管方式。维护服务器侧文档时同步实际运行事实，并注明哪些副本已核对。

部署结束后把有长期价值的环境约束、决策和错误经验交给 `dev-archive` 或直接整理到 `.agents/dev/notes/`。没有上线成功就明确标记失败、回滚或待部署，不把整个需求写成“已交付”。

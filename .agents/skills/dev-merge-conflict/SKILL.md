# 定位、解决和验证 Git 冲突

## 定位实际操作

在被指定的工作树运行 `git status`、`git ls-files -u` 和 `git diff --name-only --diff-filter=U`。从当前工作树的 Git 状态确认正在进行的 merge、rebase 或 cherry-pick，必要时用 `git rev-parse --git-path <状态文件>` 定位对应元数据。核对两侧提交和意图，保留其他人在操作前或期间的修改。普通命令失败、没有进行中的操作或仅存在语义冲突时，按实际证据处理，避免误执行继续或取消命令。

对具体路径可用 `git show ":1:<路径>"`、`git show ":2:<路径>"`、`git show ":3:<路径>"` 读取存在的索引阶段。普通双亲合并中它们分别对应基线、当前侧和合入侧。删除或新增可能没有某一阶段，重命名可能出现多条路径。rebase 中当前侧通常是正在重放到的分支，另一侧是正在重放的原提交。使用 Git 的实际内容和提交身份判断，不能按分支的口语称呼整侧覆盖。

## 解决组合后的行为

| 冲突 | 核对和处理 |
| --- | --- |
| 同一段内容或无文本标记的语义冲突 | 查双方提交、行为契约、调用方及测试。让结果同时实现仍有效的意图。例如一侧更改调用协议，另一侧加校验时，检查新协议下校验是否仍生效。 |
| 重命名、删除或文件类型变化 | 跟踪原路径、目的路径、引用和删除原因。决定保留或删除后修复引用与调用方。 |
| 锁文件或生成文件 | 先解决源文件和依赖声明，再按项目锁定版本的工具生成并检查 diff，验证冻结安装或生成物一致性。 |
| 二进制、子模块或其他无法逐行合并的内容 | 核对真实版本、用途、可用生成或审查办法及授权。证据不足时保留双方，把未决取舍交回负责人。 |

已有冲突解决记录时可复用其候选方案，逐项核对当前基线。无法从契约、测试和已确认决定判断业务意图时，记录冲突路径、两侧版本、可选结果及影响，保留可恢复现场。

## 验证并交回

1. 只暂存确认属于本操作的具体路径，包括有意删除的路径。再次核对 `git ls-files -u`、`git diff --cached` 和 `git diff --cached --check`，检查冲突标记、意外覆盖及其他人的暂存内容。
2. 在实际组合结果上运行相关契约和回归检查。报告解决的路径、保留的行为、实际检查及未决项。暂存完成与测试通过有各自的证据。
3. 调用者负责本轮 merge commit。若独立接手且授权包括执行，确认实际操作再用对应的 `git merge --continue`、`git rebase --continue` 或 `git cherry-pick --continue`。后两者遇下一处冲突时重新核对提交和索引阶段。只有操作归属、已有改动及取消结果明确时才按对应的 `--abort` 处理。

# Git 冲突处理

接收实际工作树、在途操作、两侧提交、行为契约、验证要求以及提交或继续操作的授权。先核对仓库、索引、现有修改和参与者，沿用当前 change 的证据。

按文件查明双方意图，解决冲突并验证组合后的行为。将已处理路径、暂存检查、测试和未决事项交回调用者。由 `dev-worktree` 调用时，将已验证的暂存结果交集成者生成并核对双亲提交。独立接手时，只有授权包含完成原操作才按对应命令继续。

# 逐个合并回父分支

## 确定批次和父分支

- 从当前任务记录确认共同的直接父分支、依赖顺序和本批子分支。等同一批已启动的工作树交回最终提交、检查和写入权，再由一位集成者逐个处理。依赖本批结果的工单在上游合入后进入后续批次。
- 在本批子树派发前从同一预算保留一个可复用集成树的磁盘空间，并明确集成验证的负载安排；必要时减少叶子并发。未合并子树不能先占满保留容量，否则会形成“无空间集成、未合并又不能回收”的等待闭环。
- 从 Git 登记读取父分支的实际检出。未检出时可在工作树根按[目录规则与资源准入](lifecycle.md)将它检出到本批专用目录。父树先查状态及进行中的 Git 操作。有归属明确且应保留的本任务改动时，按已有授权验证、选择路径并独立提交。有归属明确的在途冲突时调用 `dev-merge-conflict`，完成原操作。保留用户或归属不明的改动，记录它们阻塞的操作。

## 生成并验证每个双亲提交

1. 固定父分支当前完整 SHA `P`、本轮交付的子分支完整 SHA `C`。核对仓库身份、直接父分支和共同历史。若 `C` 已是父分支的祖先，核对现有提交关系，记录已集成并进入下一项。
2. 新建或初始化集成树前按[创建与接手](lifecycle.md)取得同一主机资源池的预留，包含集成验证负载；额度不足则等待，不占用活动子树。在独立的本地集成分支和工作树从 `P` 开始，使用 `git merge --no-ff --no-commit --no-overwrite-ignore "<C>"`。集成树可用于后续项，但每次必须干净且 HEAD 等于本轮 `P`；基线变化时保留已有候选引用，并从新的父提交准备。合并异常时先读实际 Git 状态，只有确实存在未合并条目才交冲突技能。两次重试之间先核对父、子和在途状态，避免双份合并。
3. 验证合并后的暂存差异、相关行为和项目门禁，包括未出现冲突标记的交互变化。确认运行测试的跟踪文件与索引一致，用 `git write-tree` 记录验证的树。测试失败时保留父分支原样，修正集成树并复验。通过后完成 merge commit，得到 `M`。用 `git rev-list --parents -n 1 "<M>"` 确认恰有两个父提交，按顺序等于 `P` 和 `C`，并核对 `M^{tree}` 等于验证的树。
4. 推进前在真实父检出重读分支、HEAD 和工作树状态。父分支仍在 `P`、父树干净且集成者持有写入权时，用 `git -C "<父检出>" merge --ff-only --no-overwrite-ignore "<M>"` 推进。这里推进的是已经生成的双亲提交，两个父提交仍在 Git 图中。父分支变化时以新提交重新集成并复验；状态、权限或文件冲突未解决时保留候选。相同的 `M` 已在父历史中时回读确认即可。
5. 回读目标分支及 `git merge-base --is-ancestor "<C>" "<父分支>"`。在同一 change 记录 `P`、`C`、`M` 三个 SHA 及验证引用，再处理下一项。用 `git log --graph --oneline --decorate "<父分支>"` 查看整体提交图。

托管 PR 合并由 `dev-deploy` 按当前授权和平台门禁执行。需要保留子提交及拓扑的目标必须支持 merge commit；线性历史、分支保护或其他门禁挡住落地时，保留已验证候选并报告实际限制。

## 完成后回收

对本次管理的子树与集成树，核对实际合并关系、检查已提交、未跟踪与忽略文件、使用状态和必要证据。按[清理方法](worktree-cleanup.md)只回收授权且可以恢复的检出，并将进程退出与实际空间复测结果交回原资源预算。工作树移除后，父分支仍可从同一提交图查看每个子分支的合入记录。

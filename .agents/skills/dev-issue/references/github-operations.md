# 创建、更新与评论 GitHub Issue

先核对目标与授权，再准备可审查的正文，最后写入并回读。使用实际可用的 GitHub 连接器或 CLI；工具名与参数以当前接口为准。

## 确认目标与读取范围

1. 从用户明确的 URL 或仓库名解析 `owner/repo` 与 Issue 编号。只有用户未指定目标时才从项目配置或当前 Git remote 取候选，核实后使用；有多个合理候选且无法判断时再问。上游参考和技能所在仓库不是默认目标。
2. 读取仓库实际默认分支、Issue 模板、相关开发规范与可用权限。更新或评论时确认 URL 指向 Issue，而非同号 PR、Discussion 或评论。引用评论时保留其所属 Issue 身份和评论 URL。
3. 读取已有 Issue 正文、作者、状态、更新时间、全部评论、关联 PR 和关键附件。列表响应有分页时跟随游标或页码直到目标范围完整，不能把第一页当全部；未取全时说明缺口，不宣称已检查完整讨论。
4. 查重覆盖 open 和 closed Issue，搜索来源链接、关键症状、功能对象和稳定任务身份。只用标题或 `T001` 不能判重；结合版本、触发、期望结果、原有处理和来源 change。结果被截断时细化查询或分页，不用“没搜到”证明不存在。
5. 确定当前写入范围。明确“发布”“更新”“评论”是对应动作的授权；仅审阅或草拟不授权远程写入。已有授权继续有效，不重复确认。锁定讨论或权限缺失时交付草稿，不能换仓库规避。

公开或共享仓库中的日志、截图和附件若确含凭据、个人信息或内部地址，先生成必要脱敏内容并核对可见性。用户提供文件可供分析不等于必须将整份附件上传；没有实际敏感内容时无需增加泛化警告。

## 选择操作

| 用户要的结果 | 实际操作 | 保留边界 |
| --- | --- | --- |
| 新建一份完整 Issue | `create` | 写入指定仓库；相同事项优先复用已有对象 |
| 完善指定 Issue | `update` | 更新已授权的正文及必要标题，保留状态与其他元数据 |
| 在 Issue 下补充意见 | `comment` | 新增一条增量评论，保留原正文和他人评论 |
| 先写草稿、只分析 | 不写远程 | 交付完整正文和拟执行操作 |

不要把授权范围外的动作作为默认补偿。比如不能因更新失败而新建重复 Issue，也不能因无法评论而编辑正文。已存在同一事项时，可以拟好更新或评论；若用户只授权创建且不能合理推知允许修改现有对象，报告查重结果并交付草稿，说明需要确定的实际动作。

标签、里程碑、指派、关联子 Issue、关闭、重开或删除是各自的操作。沿用明确请求与项目约定，只使用真实存在且适用的标识；不自动创建标签、指派他人或提及机器人触发执行。只完成撰写时不改变 Issue 开关状态。

## 创建新 Issue

先完成[内容就绪检查](authoring.md#检查内容是否就绪)。预先保存最终标题、正文及目标，在写入前再次检查当前目标与重复对象；不要在正文还未完成时创建空工单。

创建一次后保存工具返回的 Issue 身份与 URL，再回读。多个子 Issue 已获授权时按现有计划逐个创建，立即记录每个返回编号与来源票据；重试从未完成项接续，不整批重发。一个父 Issue 的授权不自动等于无限拆分和批量发布。

与来源关联时使用完整 URL 或实际仓库编号。需要稳定标记以防重试重复时，使用不含秘密的来源身份，如 change 路径和票据 ID；先搜索已有标记。不要使用会跨 change 复用的单个 `T001` 作为唯一身份。

## 更新已有正文

读取完整现有内容，在本地或当前任务记录中保留更新前快照及版本。已有来源记录时先按授权修正原记录，再形成自包含发布视图；若本地同步不可执行，写清待同步差异，不把两边都称为最终契约。

合并正文时保留仍有效的需求、已完成勾选与证据、附件链接、讨论来源和关联 PR。用户明确要求删改的部分按授权处理；仅排版润色不能改成另一套需求。只传此次需要变更的字段，避免用空数组清掉标签或指派。

写入前重新读取正文和相关最新评论，将它们与起草基线比较。发生变化时先合并再写；重大冲突保留双方证据并解决差异。可以检查 `updated_at`，但它不代替正文比对，评论或元数据也可能改变时间。

工具支持条件写入或版本检查时按其真实接口使用；不支持时，读后再写仍存在竞争窗口，不能声称原子比较交换（CAS）或并发零覆盖。保持单一写入者、缩短间隔，写后再次核对。发现期间新增的人工作业被覆盖时，基于最新正文恢复该内容或明确报告冲突；不能盲目把整份旧快照回滚上去。

用户只要求更新正文时，不额外发一条通知评论。必要的修订摘要可留在正文或本次交付中。

## 追加评论

根据原讨论填写[增量评论](../assets/comment.md)。引用正在回应的评论、源码或版本，说明新事实、建议、影响与验证；没有新增信息时说明无需重复发帖。

发送前复读最新相关评论，检查同一结论是否已发布或已被后续讨论解决。已有长篇正文只引用所需片段；不会因为是他人的 Issue 就自动改写正文。编辑某条评论是单独动作，只有明确授权且对象可编辑时才执行。

评论只描述当前用户授权的意见，不伪装成原作者、维护者或团队共识。保留原讨论状态；操作成功后记录评论 ID 与 URL，并回读正文。

## 传递正文

连接器支持结构化参数时，直接把真实多行正文传入 `body`、`comment` 或对应字段。CLI 使用 UTF-8 文件和 `--body-file`，把正文当数据传递；不把 Markdown、反引号或用户文字拼入 shell 命令。

以下是占位示例，执行前用已核实的仓库、编号、标题与本地文件替换，CLI 能力不足时使用连接器：

```sh
gh issue create --repo 'OWNER/REPO' --title '已核实的 Issue 标题' --body-file '/absolute/path/issue.md'
gh issue edit 123 --repo 'OWNER/REPO' --body-file '/absolute/path/issue.md'
gh issue comment 123 --repo 'OWNER/REPO' --body-file '/absolute/path/comment.md'
```

用文件工具写正文，再读取文件核对换行和内容。标题或路径也需要正确 shell 引用；优先用支持参数数组的执行接口，不能把 `JSON.stringify()` 当 shell 转义。读取分页时使用当前工具实际支持的分页参数，不假设某个 `view` 或 `search` 命令天然返回全部数据。

## 处理失败与结果不明

| 观察到的结果 | 下一步 |
| --- | --- |
| 参数或权限明确被拒绝，未发生写入 | 保留正文，修正可修正的输入或说明权限缺口；不扩大操作范围 |
| 网络中断、超时、返回缺少身份，无法判断是否写入 | 先查远端和本次操作记录；核对作者、时间范围、目标、正文与来源标记 |
| 查到同一新 Issue 或评论已成功 | 保存真实身份并回读，不再次创建 |
| 更新响应不明 | 读取目标最新正文；已符合预期就核对完成，否则以最新内容重新合并 |
| 能可靠确认未写入 | 对同一目标重试尚未完成的操作；多项工作保留已成功结果 |
| 仍无法确定是否写入 | 标明结果待确认，保留恢复点；停止盲目重发 |

查询“没找到”只有在搜索范围、可见性和分页足以判断时才支持未写入结论。搜索索引可能尚未反映刚创建内容，必要时读取仓库近期 Issue 或目标最新评论确认。无权回读时报告“写入已返回成功，回读未验证”，不要宣称完整交付已核实。

本次操作记录只保存恢复所需的目标、动作、正文、基线与返回身份。沿用已有 change 或临时正文文件，不新增专用状态数据库或后台重试流程。

## 回读与交付

从实际远端重新读取，确认目标仓库、Issue 身份、标题或评论正文、Markdown 换行与来源链接；更新时确认保留项和状态没有被意外改变。子 Issue 或依赖关系若确有操作，分别核对真实关联结果，正文里的文字不代表平台关系已建立。

交付实际 URL、完成的动作、内容就绪程度和仍需处理的差异。失败时说明哪一步失败、哪些已成功、是否存在不明结果及如何安全接续；草稿不能写成已发布。

只有本地权威记录已同步且远端已回读，才宣称两边一致。没有本地来源的 Issue 则以该对象的最新正文和已确认讨论为后续接手依据。

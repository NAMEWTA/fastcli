# 把需求写成可认领的 Issue

先建立证据和维护位置，再按问题类型组织正文，最后检查接手者是否还需猜测影响结果的决定。

## 建立证据与引用

读取适用的 `AGENTS.md`、项目协作说明、`CONTRIBUTING`、Issue 模板和相关开发约束。`CLAUDE.md`、`GEMINI.md` 或其他宿主指令按项目实际使用情况读取，不要求项目补齐所有文件。遵守项目的目录、插件边界、依赖、UI、数据与验证约定。

查阅目标模块、已有同类实现、相关规格、变更记录和测试入口。记录能重新定位的版本、路径与符号；源码永久链接固定已读取的提交。拟新增文件明确写“拟新增”，不要把预想的目录、接口和运行结果写成当前事实。

来源分类写清楚：

| 证据类型 | 写法 |
| --- | --- |
| 当前代码或实际运行 | 版本、定位、观察结果，以及证据能证明的范围 |
| 用户提供的报告 | 原话所表达的症状与来源，标明尚未复现的部分 |
| 推断或候选方案 | 推断依据、需要怎样验证，以及尚未排除的解释 |
| 已确认决定 | 决定内容、来源、适用范围和版本 |
| 无法访问的材料 | 缺失内容与对就绪程度的影响，不宣称读过 |

复用顺序遵守目标项目约定。先查当前已有实现和项目指定来源，再判断成熟依赖与开源项目；给出采用或不采用的实际理由。每个重要外部参照提供完整 URL、读取日期、固定 commit 或版本、具体文件或章节、拟复用行为和必要适配。UI 参照说明页面、状态与交互；代码复用说明接口、依赖和许可要求。网址本身不能替代设计判断，未经读取的路径不能当证据。

已有确认原型时，就近引用对应版本、页面与状态及确认范围。原型只证明实际覆盖的体验；后端、权限、持久化和失败语义仍需行为约定。用户没有确认的探索产物按探索结果引用。

## 组织自包含正文

使用[正文模板](../assets/issue.md)或目标仓库模板。两者发生栏目差异时，保留仓库必需信息，把实施所需内容放入合适章节。小问题可用短段落，大需求再展开表格；删掉占位文字与不适用章节。

1. 用具体标题说明对象和预期改变。开头交代谁在何种场景遇到什么问题，以及解决后的价值。
2. 写当前行为与证据，再写目标行为。用户明确要求的新契约优先作为目标，旧代码用于解释差距。
3. 列出本次范围、必要约束和明确排除项。新增布局、数据迁移、删除旧能力或破坏性变更要写出影响；兼容策略由项目要求和用户决定。
4. 用场景描述主流程、边界与异常。涉及权限、数据或接口时，写参与者、输入、输出、授权、失败与恢复语义，按实际需求展开。
5. 说明拟复用的模块、依赖、接口或 UI，并给出取舍理由。架构设计聚焦职责和关键决策；把当前文件导航与未来行为分开。
6. 整理实施清单、真实前置条件、各项产出和验证。最后写可观察的验收标准、风险和仍未解决的问题。

Issue 必须能被独立接手。已存在本地权威记录时，标明来源路径、提交或明确快照日期，以及哪份记录维护行为、任务和进度；提供接手者可访问的链接。资料只存在本机或权限受限时，将完成本项所需的内容写入 Issue。发布摘要保持来源含义，并明确后续更新回到原记录，不另建立一个独立计划。

不要把完整性理解为固定篇幅。一个明确缺陷可以只包含复现、目标、影响、修复线索和验收；跨模块功能再补详细数据与接口。已有事实足够时直接成稿，缺少架构细节不等于必须问用户选技术。

## 按类型补足信息

### 新功能与交互改造

描述参与者、触发入口、目标和主流程。按实际行为检查空态、加载、失败、取消、重试、权限不足与边界数据；不适用的状态不硬加。

对新接口写输入输出、错误和必要兼容约束。对数据写归属、生命周期和迁移影响。对 UI 引用当前设计系统、可复用组件及具体原型状态；涉及尚未确定的体验决定时标明实施前提，不能冒称已经取得确认。

需求使用稳定编号或清楚标题，让验收能逐项对应；编号只在确有追溯需要时使用。例：“切换工作区后，仅显示该工作区的会话；返回原工作区可恢复此前选中的会话。”比“优化工作区体验”更便于实施与判断。

### Bug

至少记录报告版本与环境、前置条件、操作步骤、实际行为、预期行为、影响范围和可用证据。已知概率或回归范围有依据才填写；未知写明未知。

把报告、复现与根因分开：用户说失败是报告；实际按步骤观察到失败才是复现；能够解释触发机制并有证据支持才是已确认根因。相关代码只是调查线索时保留候选措辞。缺少必要输入先查项目与日志，再问无法自行取得的内容。

验收覆盖原失败场景、相邻正常场景和修复可能影响的行为。是否新增自动回归、使用 TDD 或实现后验证按项目和风险决定；不强制为每个文字或样式改动建立测试。

仍不能复现时，可以形成调查任务：列出待取得的环境、最小复现与预期诊断产出，标明“待调查”。不要用猜测的代码修复清单冒充已就绪方案。

### 性能优化

把“慢”转成一个明确场景：入口、版本、硬件或服务资源、数据规模、负载与并发、冷热状态、测量工具和采样方法。记录相关指标，如延迟分位数、吞吐、内存或 CPU；只保留与用户目标有关的指标。

区分实测基线、用户目标与尚待确认的阈值。已有数字要附测量条件；没有基线时安排获取基线和定位瓶颈的任务。方案涉及算法或依赖选择时，说明还需要哪些数据才能决定。

写清比较方法和正确性约束，例如同一数据集与负载下对照修改前后，输出一致且错误率不增加。需要统计稳定性时写重复次数或采样窗口的依据；不要凭空规定通用百分比。

没有足够证据确定优化方案时，将事项标为待测量或待调查；可以让开发者先认领测量工作，不能承诺尚未证实的收益。实际测量方法可交 `dev-benchmark`，取得结果后更新同一记录。

### 重构、依赖升级与技术债

说明当前结构造成的具体问题、允许改变的边界和必须保持的外部行为。列出受影响的调用者、数据、接口、文档和运行环境，引用实际定位。

用户允许破坏性替换时，写清新契约、删除项及调用者迁移。项目需要过渡兼容时，说明持续时间、退出条件和回退；不要自动添加兼容层。

跨模块任务沿用 `dev-plan` 的票据与整合边界。某中间提交无法独立运行时写清最终整合验收点，不能把它描述成可部署的完成项。

## 引用计划与验收

已有票据或计划时直接引用稳定身份与当前版本。任务清单是来源快照，依赖与进度回到原记录维护。没有计划且只有一个明确 Issue 时，可在正文内列必要实施步骤，不强制建立票据文件。

确需拆成多个独立认领项、调整切片或生成 DAG 时交 `dev-plan`，带回本地票据与依赖。远程子 Issue 仅按用户授权发布；创建顺序遵守已有依赖，使用实际编号，原生关联可用时才使用。任务数量不是交付标准。

每个实施项应说明交付内容、所需前置产物、完成证据和负责范围。并行判断要检查共享接口、模型、迁移和验证资源；不同文件并不证明可并行。本技能沿用计划结论，有冲突先回原计划修正。

每项验收都写条件、动作和可观察结果。可以用 Given/When/Then，也可以用清楚的一句话。验证说明实际入口、必要命令或人工步骤、通过判据与预期证据；存在的命令从项目核实，拟新增的测试写明拟新增。计划中的验证不得标作已通过。

例如，缺陷验收可以写“输入空名称保存时显示字段错误且不创建条目；输入有效名称仍能创建”，不要只写“校验正常”。性能验收需同时限定负载、指标、目标和正确性，不能只写“更快”。

## 检查内容是否就绪

发布前逐项检查，缺口按对开发的影响处理，不按模板是否填满判断：

- 目标仓库、操作、问题类型和本次范围明确，已有同类 Issue 与当前实现已检查。
- 现状、目标、推断、已确认决定和待验证内容区分清楚；来源能访问或已补足必要原文。
- 项目规范、复用路径、完整上游地址和必要适配已落实；没有假文件、假复现、假基线或假确认。
- 需求、任务产出、验收与验证对应，正常路径和重要异常已覆盖；实施者不必猜核心产品决定。
- 本地权威记录与发布视图一致，来源版本清楚；不能同步的差异及影响已声明。
- 内容符合目标模板，附件和来源信息适合发布到该仓库；仅对实际出现的凭据或私人数据做脱敏与必要处理。

满足实施所需前提时标明“可认领实施”。仅调查或测量已清楚时标明“可认领调查”，并限制交付为证据和决定。关键范围、行为或验收仍需用户决定时交付“待澄清”草稿与具体问题。远程发布是否继续取决于用户请求；不能为了发出一个 Issue 而擅自把功能需求改成调查任务。

## 已有 Issue 的修订与评论

修订正文前整理原需求、后续决定、已完成项、附件与关联 PR 的进展。形成一份当前可用的完整正文，必要时用简短变更说明解释重要调整；保留仍有效的信息，不层层追加互相冲突的计划。

正文与来源冲突时，查最新用户决定和实施证据。已确认的新决定按授权同步到原记录。无法判定时列明冲突，保留有效进展，不能把远端完成项覆盖成陈旧快照。

追加评论使用[评论模板](../assets/comment.md)，指出所回应的具体问题、此次新证据、建议和验证方式。建议和维护者已接受的决定分别表述；只提供有增量价值的内容，不重发整个 Issue。写入、分页、并发和失败恢复按[操作方法](github-operations.md)执行。
